# Changelog

## v4.2.3 (DEV)

### Added
- **Reject more than just live versions**: the "Reject Live Versions" toggle has grown a companion, a free text box where you list whatever else you cannot be doing with. `demo, acoustic, radio edit, remix` is a reasonable start. A downloaded track confidently identified as one of those gets binned and retried, exactly like the live check. It inherits the same paranoia too: the keyword only counts inside a version annotation such as `(Acoustic)`, `[Demo]` or `- Radio Edit`, so "Demolition Man" is in no danger from the word "demo" and "Radio Ga Ga" is safe from "radio edit"; it only ever acts on a confident AcoustID fingerprint, never a text-search guess; and anything you explicitly asked for by name is never rejected, so searching for the acoustic version still gets you the acoustic version. "remix" matches "(Tiesto Remix)" without you having to know who Tiesto is. Requested by kaisernerox on GitLab (#96).

### Fixed
- **Personalised YouTube Music playlists no longer download a stranger's taste**: Discover Mix, My Supermix, Liked Music and the rest are the same playlist ID for every account, and YouTube serves a logged-out request a perfectly plausible list of the wrong songs rather than an error. MusicGrabber's yt-dlp retry policy would drop your cookies and retry anonymously whenever a request looked session-related, that anonymous retry would "succeed", and the generic recommendations got queued up as your playlist. Worse, succeeding without cookies put the cookies in the sin bin for two hours, so the next few checks went the same way. These playlists now insist on your cookies, keep their `music.youtube.com` URL intact, never fall back to asking anonymously, and fail with an actual "your cookies were not accepted" message instead. Nothing gets queued and no sync state is touched when that happens, so the last good state survives until you sort the cookies out. Reported by michael.j.strong on GitLab (#95), who correctly called the anonymous fallback as the suspect.
- **Apple Music playlists over 300 tracks**: Apple's public catalog API has stopped accepting the anonymous web token MusicGrabber scrapes from their own site, so the API path was quietly 401ing for everyone and falling back to HTML scraping, which Apple caps at 300 tracks. A 500 track playlist arrived as 299 tracks with no indication that the other 201 existed. Your Apple Music user token is now sent on public playlists too, not just private library ones, and if we do end up scraping the page and come back suspiciously close to Apple's cap, we say so rather than presenting a truncated list as the finished article. The Settings hint has also been corrected: the header is called `media-user-token` in DevTools these days, which is what sent the reporter looking for something that was not there. Reported by NLco on GitLab (#94).

## v4.2.2 (2026-09-15)

### Added
- **Search the queue**: the Queue tab now has a search box, for the entirely reasonable case of "I imported 900 tracks, one of them came back as the wrong song, and I am not scrolling through 90 pages to find it." Type a few letters of the artist, title, album or playlist name and the queue narrows to the matches, with a count so you know where you stand. Crucially it searches the *whole* job history rather than just the newest 250 jobs the tab has loaded, which is the bit that makes it useful at all: on a real 2,794-job queue a search for "creep" turned up 212 jobs that the Queue tab previously had no way of reaching. Clear it with the x, or with Escape. Suggested by Snuupy on Reddit, who asked the obvious follow-up question to "just find it in the queue tab".

### Fixed
- **Queue search keeps up with you**: a slow response for an earlier search no longer appears under your latest search text; changing or clearing the search fetches the latest results as soon as the pending request finishes. API searches scoped to a bulk import also work without a database error.
- **The live queue summary no longer counts only what it can see**: the "3 on the workbench, 40 waiting" banner and the queue-size limit were both counting the newest 250 jobs rather than the queue, so a genuinely enormous queue quietly under-reported itself. Both now use real totals from the server, which also means searching the queue down to a single card no longer convinces the banner that everything else has emigrated.
- **The Queue tab header no longer runs off the side of a phone**: the row of controls above the queue has been overflowing at narrow widths for a while; it now wraps like a civilised thing.

## v4.2.1 (2026-09-14)

### Added
- **"Convert lossless sources only"**: a new toggle next to the audio format picker, for when "Convert to" is set to a lossy format (Opus, MP3, or AAC-in-M4A ALAC). Switch it on and only genuinely lossless sources (FLAC, ALAC, WAV) get re-encoded; a source that arrived already lossy (MP3, AAC, an existing Opus) is kept exactly as delivered instead of being hopped into a different lossy format for no quality gain, and occasionally for a bigger file than it started as. Off by default, so nothing changes unless you flip it. Requested by dynAdZ on GitLab (#92), who put it rather well: converting a lossy source to a different lossy codec "cannot improve the original quality and introduces another lossy encoding generation."
- **Bulk Import now shows its working, properly**: every track in a bulk import gets its own row as it goes, and the moment a track has a real download job behind it, that row becomes the exact same card the Queue tab shows: full status, source, and a proper Retry / Re-download / Report / Edit Tags button set, not a second, thinner copy of that UI. A track still being searched gets a simple placeholder row instead, which swaps for the real thing the instant a job exists. And the tab no longer forgets what it was doing if you reload the page or come back later: it now reconnects to a still-running import automatically instead of leaving you to go hunting for it in the Queue tab. Prompted by dodonut's GitLab #91, half of which turned out to already be possible (job retry lives on every job's own card), and half of which was a genuine gap this closes.

### Fixed
- **The persistent library index's first build could starve itself to death on a big library**: while a root's very first reconciliation was still running, the old full-library duplicate-check fallback would happily start its own competing walk of the same disk every time a bulk import checked a track for a match. Reported against a 34,428-file library, where the two scans fought each other over disk I/O so badly that the reconciliation never finished, `library_roots` stayed empty, and bulk imports sat at "Checking for duplicates" while the array pegged at 95-99% utilisation. The fallback now checks whether a reconciliation already owns the root before starting a second walk, and simply declines (serving whatever it already has cached) rather than piling on. Thanks to russelljennings for the diagnosis and reference fix (GitLab #93).

## v4.2.0 (2026-09-13)

### Added
- **The riskiest function in MusicGrabber finally has tests**: `perform_upgrade` is the one place that deliberately overwrites a file you already had, and it was the only part of Track Upgrades with no test at all, because reaching the actual swap needs a candidate row, a staged download, a content hash and an audio fingerprint all lined up at once. It now has nineteen, and they use real audio throughout: ffmpeg generates the files, and the quality comparison, the content hash, the retagging and Chromaprint all run for real rather than being agreed with by a mock. Both the old and new files are encoded from one master, which real Chromaprint scores at 1.0000 similarity, while the "that's a different recording" test uses genuinely different audio, which it scores at 0.5854 against the 0.65 floor it has to clear. Every gate was then checked by breaking it on purpose and confirming a test noticed: the better-than-what-you-have check, the duration and fingerprint identity checks, the pre-swap revalidation, the quarantine record that makes the whole thing undoable, the retagging, the playlist rewrite, the Queue history, and the temporary-folder cleanup. That exercise immediately found a hole in the tests themselves, where the "not actually better" case was being refused a gate earlier for an entirely different reason, so the test passed with the gate it was named after switched off completely.

### Added
- **Find New Artists**: the Artists tab now has two halves, switched with a pill: the Followed Artists you already had, and a new place to go looking. It works out who you actually listen to (Navidrome play counts if you use it, otherwise what fills your library, otherwise what you have downloaded), finds artists like them, throws away everyone you already own, and lays the rest out in rows that say why each one is there: "Because you listen to Pendulum" gets you Netsky, Noisia, Camo & Krooked. Every artist comes with a thirty-second preview to hear before you commit, and a Grab it button that hands the track to the ordinary download pipeline, so a discovery arrives as a properly tagged, properly routed, best-available-quality file exactly like anything else you queue. Compilations are ignored when working out your taste, since "Various Artists" tells us nothing except that you own a lot of compilations.
- **And a rabbit hole to fall down**: click any suggested artist's name and you get *their* similar artists as a new row, with a breadcrumb back out. Keep clicking and keep going. There is also a "recommend based on" box for when you have a specific lead you fancy chasing.
- **Grab a whole row in one go**: every row of suggestions now has a "Grab the lot" button, the same offer the Similar-artists bar makes, since ten cards each needing a click is a poor reward for finding ten things you like. It resolves a real track for each artist first rather than sending ten bare names off to be guessed at, skips any you already own or have already queued from the card itself, and hands the lot to bulk import as one playlist named after what it came from, e.g. "Similar to Shaboozey (2026-09-13)". It leaves you where you were rather than flinging you at the Queue tab, on the grounds that you were in the middle of something.
- **A different set of rows every time you look**: the rows were built from your top five artists, which meant the same five rows on every visit, going stale at roughly the speed you would expect. It now draws them at random from the forty artists you play most, weighted by rank rather than by play count, so your favourites still come up often without one heavily-played artist winning every single draw. Three consecutive loads on a real library gave Nirvana/The Prodigy/Naughty Boy/Ellie Goulding/Chase & Status, then Shaboozey/Therapy?/Massive Attack/Bring Me the Horizon/Pendulum, then Knife Party/Shaboozey/Therapy?/Nirvana/Massive Attack. Same taste, different evening.
- **The new row now announces itself**: asking for recommendations, or falling further down the rabbit hole, jumped the new row hard against the top of the window, taking the box you had just typed into off the screen with it, and moved so fast that the arrival was over before the eye caught it. It now moves at a pace you can follow, stops short so the thing you clicked is still on screen, and wears the accent ring for a couple of seconds so there is no question which row is the new one. Grab the wheel mid-flight and your scroll wins immediately, and anyone who has asked their system not to be swooshed about gets taken straight there.
- **Rows lead with artists you might actually have heard of**: Deezer's own ordering is neither similarity nor popularity, and it opened the Shaboozey row with a covers act of 971 fans whose biggest number is somebody else's song, ahead of Jelly Roll's 227,785. The obscure ones are all still there, just further along the shelf, which is the right way round for something you scroll through.

### Changed
- **"Similar artists" now actually finds some**: the Explore button asked ListenBrainz, and on a real library ListenBrainz had nothing whatsoever to say about five of its owner's eight favourite artists, silently. It now asks Deezer first, which needs no account, no key and no sign-up, and falls back to ListenBrainz for the odd artist Deezer has never heard of. The same eight artists that used to get three answers between them now get eight out of eight, in about a quarter of a second each, and clicking from artist to artist is instant because the answers are remembered for an hour. Pendulum, which previously returned nothing at all, now suggests The Qemists, Camo & Krooked and Sub Focus, which is rather more the idea.
- **Similar artists you have not already got**: a recommendation you own is not a recommendation, and measured across eight real seeds, 61% of what MusicGrabber suggested was already in the library, rising to 80% for Nirvana and 90% for Taylor Swift. Ask about Therapy? and it offered Nirvana, Faith No More and The Smashing Pumpkins, all of them already on the shelf. Suggestions are now checked against the library index and the ones you own are dropped, so the same question now answers Life of Agony, Primus, L7 and Urban Dance Squad. Collaborations count: a library holding "Pendulum feat. Jasmine Yee" owns Pendulum, which quietly rescued Duke Dumont and The Qemists from being offered as new discoveries. If the index cannot say what you own, nothing is filtered rather than everything, because a few familiar names beat an empty page.
- **Every suggested artist now comes with a track to actually hear**: a thirty-second preview, straight from Deezer, no account and no key. Deliberately not always their biggest hit, because the most famous song is the one you are most likely to already have, and a track you own is a wasted introduction. It offers the highest-ranked track you have *not* got; Radiohead accordingly leads with "Let Down" rather than "Creep". If you own all ten of their best-known tracks, as was the case with Nirvana, it hands over the hit anyway and says plainly that you have it, rather than digging up an obscurity nobody chose.
- **And it now finds the right artist to be similar to**: looking up "Pendulum" on Deezer hands back an artist with eighteen fans and no connections to anybody, ahead of the actual Pendulum with three hundred and seventy thousand. "Nirvana" gives you a different band from the sixties with two hundred fans, ahead of the one with ten million. MusicGrabber now considers the ten best candidates and picks on the name first, using popularity only to choose between genuine matches, which is how it should have been reading search results all along. It also now declines to guess: a name nothing in the catalogue matches gets no suggestions rather than confident nonsense, after a compilation credit for one "Jay Burnett" was matched to a similarly-spelled artist and produced an entire row of Spanish-language worship music.

- **Amazon playlists are now read one way instead of two**: alongside reading the rendered page, MusicGrabber also eavesdropped on every JSON response the Amazon Music app made, sifting each one recursively for anything that looked like a track. It was added as insurance and kept on probation, on the reasonable theory that it might be the only thing that worked on some playlist shape nobody had tried yet. The probation is over and it has been let go. On a live 60-track playlist it found precisely zero tracks, every single one having come from the page itself; and on a playlist that no longer resolves, where the page gave up nothing at all, it also found nothing, which was exactly the scenario it existed to rescue. Verified by scraping the same real playlist before and after: 60 tracks, identical titles, identical running order. Sixty lines lighter, one fewer thing to be confused by, and the scroll loop now measures its own progress instead of counting a collector that was never contributing to it.

### Fixed
- **Discovery cards no longer go wonky when an artist has a long name**: "Olly Alexander (Years & Years)" stretched its card to twice the width of its neighbours, because a flex item will not shrink below its own content and the name is deliberately set not to wrap. The ellipsis it already had was never getting a chance to do its job. Every card in a row is now the same size, which is rather the point of a row.
- **"Similar artists" no longer gets scribbled over by the search you just walked away from**: the Similar button takes over the results pane, but the search that filled it was often still running, because Soulseek takes its time and the results stream in per source as they land. The abandoned search then finished, cheerfully re-rendered its own results straight over the top of the similar artists, and put the "related searches" box back up for good measure, leaving the Similar bar sitting above a results list that had nothing to do with it. What you saw was the track you had just searched for, over and over, once per Soulseek peer offering it, which looks exactly like the feature returning the same track twenty times. Reproduced in a browser before fixing: 21 of 45 cards were the original track. Starting a new search always retired the one before it; walking away to Similar now does the same, which is all it ever needed to do. Zero leakage afterwards, same test.

## v4.1.2 (2026-09-12)

### Added
- **MusicGrabber now remembers what is in your library between scans**: new in this release is a persistent library index, a separate throwaway database that records one row per audio file (size, timestamp, codec, bitrate, tags, and whether MusicGrabber downloaded it). It reconciles itself against the disk once a day, opening only files that are genuinely new or changed. A file that has merely been renamed or moved by another organiser is recognised by its size and timestamp and keeps everything already known about it, so an overnight tidy-up no longer means re-reading the entire collection. The index lives in its own database file on purpose: it shares no locks with the one holding your jobs and history, it can never block a download, and if it is ever damaged the fix is to delete it and let it rebuild. Nothing anywhere waits for it; if it is missing, cold, locked or corrupt, every feature falls back to the behaviour it had before and carries on. Stats storage figures and duplicate detection by Artist/Title now read from it. Completed tag results remain usable during refreshes and regardless of age.

### Changed
- **Duplicate tag checks now query the persistent library index**: all artist-credit variants are looked up together, and matching files are checked for existence and containment before reuse. A usable completed index answers hits and misses without starting the old full-library tag crawl, including immediately after restart. Old results remain usable during refreshes; missing, cold, locked or corrupt indexes retain the non-blocking background fallback. External file changes become visible at the daily reconciliation; MusicGrabber's own writes update it immediately, as below. The cheap filename and known-path checks still go first. The NAS may finally get an afternoon off.
- **The Track Upgrades scan now asks the library index instead of the disk**: the scan can only ever act on files MusicGrabber downloaded itself, which on a real library is a small minority of them. It nevertheless opened every other file on every pass to re-confirm that they were still not ours, forever, which is the most thankless work in the entire application. The index already recorded that answer the last time it read each file, so the scan now takes its word for it whenever the size and timestamp still match to the nanosecond, a stricter test than the scan's own cache uses. Measured on a real library over SMB: a steady-state pass over 1,673 files went from 33.6 seconds to 2.2, with 1,287 file reads replaced by index lookups. Files that are genuinely new or changed are opened exactly as before, and a missing, cold or locked index puts the old behaviour back with no loss of correctness, only of speed.
- **The admin library rebuild no longer walks the library either**: "Clean rebuild" mints Queue history for audio that has none, usually after somebody moved a pile of music in by hand, and it used to walk all three configured folders and ask the filesystem to resolve every single file on the way past. It now reads the index, which agreed with the walk on every one of 1,813 paths when the two were compared directly on a real library. That per-file resolve is gone with it, but not the resolving: a downloaded file's stored path is recorded resolved, so a library reached through a symlink has to be compared resolved or every file already in your history quietly earns a second row. The folder is now resolved once instead of every file in it, which comes to the same answer for a few thousand fewer round trips, because no scan ever follows a symlinked directory and so nothing inside one can lead anywhere else. A folder the index cannot vouch for still gets walked, because "there is no audio in there" and "I was unable to look" must never be the same answer when the result becomes rows in a database.
- **The library index now follows MusicGrabber's own writes as they happen**: it reconciles against the disk once a day, which is the right interval for changes made by other software but a silly one for changes made by us. Finishing a download, trashing a track, restoring one, replacing a file with a better copy, undoing that replacement and correcting tags by hand all now tell the index immediately, so the file MusicGrabber wrote thirty seconds ago is not re-read from the NAS tomorrow to discover what it already knew. The arrival is recorded when the download is finally recorded as complete, rather than when the file first lands, because everything up to that point may still delete it again after an integrity check; a job that fails, or one whose file is a playlist rather than audio, is not recorded at all. Every one of these is a hint and not a promise: if the index is missing, locked or corrupt, the hook shrugs and the daily pass picks the change up as it always did. Costs measured against a real 20,470-file index over SMB, across ten actual library files: 67ms to read and record a genuinely new arrival, 0.9ms when the file is one the index already describes and nothing needs opening, 3.7ms to forget one. That middle number matters more than it looks: a download that turns out to be a duplicate you already own still records a completed job, and a bulk import of mostly-owned tracks would otherwise have paid to reopen every one of them for nothing.
- **A long library index build now tells you it is still alive**: a first pass over a large collection is twenty-odd minutes of reading every file once, and it used to do that in complete silence, which is indistinguishable from being wedged. It now logs how many files it has seen, read, matched as moved and skipped as unchanged, every thirty seconds (`LIBRARY_INDEX_PROGRESS_SECONDS`). A pass that finishes faster than that still says nothing, because nobody needs a progress bar for something that has already finished. The README also now spells out how to force a full rebuild by deleting the index database, which is safe precisely because the index is derived from your audio files and nothing else. Both ideas lifted, with thanks, from Michael Strong's independent `persistent-library-index` work, which arrived at the same problem from the other end and had rather better manners about saying what it was doing.

### Fixed
- **Correcting a track's tags no longer leaves its old name haunting duplicate detection**: the library index records the Artist and Title each file carries, and duplicate checks trust it, deliberately, since a completed index that says "not here" must not be allowed to trigger another full-library crawl. Retagging a file through the Queue changed the tags and the filename but left the index describing the file it used to be, so a later, entirely unrelated download of the old name could be refused as a duplicate of a track that no longer existed. A retag now replaces that row outright rather than relocating it, because the file's contents changed and not merely its name. Only possible at all since the index landed earlier in this same release, so nobody has been bitten by it in the wild.
- **Failed database opens no longer leave imaginary connections in the pool**: after eight failed attempts, later settings lookups used to wait 15 seconds for connections that had never existed. Pool capacity is now counted only after a successful open. Found when two cookie unit tests accidentally queried the container-only database from the host; those tests now supply their own settings too.
- **Watched YouTube playlists now use their owner's cookies when fetching tracks**: refreshes previously used only the shared cookie file, even when the owner had uploaded their own. Personal cookies now reach the playlist lookup too, with the existing shared-cookie fallback retained. Identification is more useful when you actually show it at the door.
- **YouTube downloads have not been using your cookies since March** (issue #90, reported by dynAdZ): every YouTube download ran without the cookie file you configured, and without the player-client override that goes with it. If you pay for YouTube Premium you were getting the ordinary ~128 kbps Opus stream instead of the ~250 kbps one you are entitled to; if you do not, you were facing YouTube's "sign in to confirm you're not a bot" checks with no credentials to show it. The cause is a small and very boring one. The rule was originally written as "use cookies unless this is SoundCloud", which was correct. v2.0.0 reworded it to "use cookies unless this has a source URL", which was still correct at the time because YouTube downloads did not have one. Then v2.3.0 started attaching a source URL to every YouTube job purely for record-keeping, and the reworded rule quietly began excluding the one source it was written to include. Six months later somebody with a Premium account noticed the bitrate was wrong and tracked it down for us, including the fix. The rule now lives in one named place that says what it means, with tests that fail if anyone rewords it again.
- **Per-user YouTube cookies were never actually used**: the same code knew perfectly well which user a download belonged to, and then asked for the cookie file without mentioning it, so everyone got the shared one. Spotted in the same report. Playlist downloads had it too, and are fixed alongside.
- **The library index could not build at all on some network shares**: SQLite stores whole numbers as signed 64-bit, while some SMB/CIFS mounts invent inode numbers by hashing the file handle when the server will not supply real ones, which uses the full *unsigned* range. About one file in a hundred and fifty then failed to save, and because the save happens in batches, that one file took the entire nightly rebuild down with it. Every night. Forever. The index simply never appeared, logged its complaint politely and everything else carried on none the wiser, which is the correct behaviour and also why it could have gone unnoticed indefinitely. Those numbers are now stored as the same bits read the other way round, which keeps every file distinct and costs nothing. Caught by deploying to a test machine whose mount hashes, having been completely invisible on the machine beside it, where the very same NAS hands over real inode numbers.
- **An out-of-date duplicate index can no longer turn into a failed lookup**: a tag index past its five-minute freshness window is still the best answer anybody has, so it now answers, and the refresh happens behind it. This was already the behaviour after the background-scanning work earlier in this release; it is now pinned down by a test so a future tidy-up cannot quietly reintroduce a hard failure. Same argument Michael Strong made in his branch, approached from the other direction.
- **Library scanning no longer blocks downloads**: duplicate checks still use quick filename and path matches plus the last complete tag index, but a cold or stale full-library index now refreshes entirely in the background. Downloads and API actions carry on immediately instead of waiting for up to fifteen minutes or failing because the NAS has a large record collection. The trade-off is honest: an externally renamed duplicate may escape detection until the first background index completes.
- **Track Upgrades stopped reading your entire library every single day**: the interval scan re-probed *and* re-hashed every eligible file on every pass, on the reasoning that someone might replace a file while preserving its path and timestamps. Technically true, ruinously expensive: on a 600 GB library that is 600 GB dragged across the mount daily so the Watched Upgrades page could confirm that absolutely nothing had happened. Files whose size and modification time both match the previous scan are now re-ranked against your current quality target from data already stored, without being opened at all. Only genuinely new or changed files get the full treatment. Spinning disks in RAID5 have suffered enough. The stored hash is still checked against the real file immediately before any replacement, which is the moment it actually protects something; the honest cost is that a replacement preserving both size and timestamp to the byte goes unnoticed until something else disturbs the file, and anything that goes to that much trouble to be invisible has earned it.
- **Library walks now ask the disk once per file instead of six to ten times**: every full-library scan went through one shared walker that handed back a bare path and threw the file's details away, so each consumer then had to go back and ask the disk for the size and timestamp it had just looked at. Add the separate "is it a symlink", "is it a file" and "where does this really point" questions and a single pass over 1,675 files came to 16,475 metadata operations, which is 9.84 per file to answer questions the operating system had already answered once. The walker now reads directories properly and passes on what it found, bringing the same pass down to 2,547 operations, or 1.52 per file. On a local SSD that was always noise; over a network mount it is six or seven fewer round trips per track, every track, every scan. Storage totals on the Stats tab, the duplicate tag index, the Track Upgrades scan and the admin library rebuild all benefit, since all four share the walker. Measured on a real library, not estimated from first principles.
- **The Track Upgrades scan no longer syncs the database once per file**: it saved each file's row the moment it read it, and SQLite flushes to disk on every save, so a twenty thousand track library meant twenty thousand separate flushes to record that almost nothing had changed. Rows are now written in batches of 500, taking one full pass from 384 flushes to one. A crash mid-batch loses at most that batch, which the next scan rebuilds from the files themselves anyway. Combined with the change above, a scan of an unchanged library went from 98.8 seconds to 34.2.
- **The Stats storage total no longer crawls your library to count it**: "storage used" and the file count walked every audio file under your library directories, refreshing every five minutes for as long as anyone had the page open, to produce two numbers. They now come from the library index in about a millisecond. If the index has not finished its first pass, or your library directories sit somewhere it does not cover, the old walk still runs and the figures are identical either way; verified against an independent count, to the byte.
- **Turning Track Upgrades off now stops its active library pass**: the scanner used to check the toggle only before starting, so switching it off merely changed the setting while the existing scan carried cheerfully on. Upgrade scans now stop cooperatively and yield to the separate background duplicate tag index, because two optional librarians elbowing through the same NAS is nobody's idea of efficiency.

## v4.1.1 (2026-09-10)

### Added
- **Track numbers in filenames now get a leading zero** (issue #86): with "include track number in filename" switched on, `1 - Track.flac` is now `01 - Track.flac`, so it sorts before `10 - Track.flac` instead of after it, the way any self-respecting filesystem ought to. Albums over 99 tracks (looking at you, box sets) pad wider still, e.g. `007 - Track.flac` for a 120-track release. Lyrics files inherit the same padded name automatically, no separate fix needed.

### Fixed
- **Jellyfin 12 library refreshes work again** (issue #88): connection tests and automatic scans now use Jellyfin's current `Authorization: MediaBrowser` API token header. Jellyfin 12 disables the old `X-Emby-Token` header by default; older Jellyfin releases accept the new header too, so no server setting or new API key is needed.
- **Slow library scans stop holding the UI hostage**: playlist files and Stats storage totals now refresh in the background, with loading/failure states and the last complete snapshot retained during refresh. Stats releases its database connection before filesystem work. Snapshots refresh on requests after five minutes.
- **Duplicate tag scans share the work and have a bounded wait**: one scan per user/library, cache age measured from completion, and a five-second lookup wait. An unfinished scan produces an explicit retry message rather than a false missing-track result; failed scans do not publish an empty index. The scan continues in the background.
- **Playlist loading waits for authentication**: the destination picker no longer sends an eager request before session validation. A late 401 from an older session also cannot clear a newly established session.
- **Fancy Unicode hyphens in artist/track names no longer corrupt filenames on disk** (issue #87): reported as "alt-J" downloading to a folder that showed up as "alt?J" over SFTP. MusicBrainz and plenty of YouTube uploaders use "smart" dash characters (en dash, em dash, the proper Unicode hyphen) that look identical to a normal `-` in a terminal but are a different character underneath, and plenty of SFTP clients, older SMB shares and non-UTF-8-locale tools choke on them and print `?` instead. Filenames now fold these down to a plain ASCII hyphen before hitting disk. Existing folders already affected are not renamed automatically; the next matching download will use the corrected name.

## v4.1.0 (2026-09-03)

### Added
- **Renamed library files are now found by the metadata they carry**: filename matching remains the quick route, but a miss now builds a safe whole-library index from embedded Artist and Title tags. MusicBee, beets or another organiser can rename `Artist - Title.flac`, move it elsewhere beneath the music root, and MusicGrabber still recognises the recording instead of downloading a second copy. The index skips trash, NAS recycle bins and symlinks. The persistent lookup above is now the normal route; the five-minute in-memory cache and refresh-on-missing-path behaviour remain only as the unavailable-index fallback.
- **Each watched playlist now has its own missing-file policy**: the new card control can inherit the global setting, re-download files MusicGrabber can no longer find, or leave previously downloaded tracks alone. Existing playlists inherit the global default, so upgrades change nothing until asked.
- **Watched Artists now own up to missing files too**: artist cards show the count of downloaded singles which can no longer be found when automatic re-downloads are disabled, rather than quietly looking complete while the path has gone walkabout.
- **Queue history sorting**: the Queue now lets you bring failed, completed, or completed-with-errors jobs to the front of its history. Queued and downloading work remains pinned above the history whatever you choose, so the useful bit cannot slip off to page two while you are tidying up yesterday's mishaps.
- **The album browser now shows cover art**: each row in an artist's discography gets a small thumbnail alongside its title, sourced from the same iTunes/Deezer chain that already covers search results. The album titles and years still render the instant MusicBrainz replies; covers trickle in afterwards, up to eight lookups at a time, so a prolific artist's back catalogue never sits waiting on the slowest cover to resolve before you can read a word of it. A handful of proper bootleg-grade obscurities (webcasts, outtake compilations and the like) simply have no official art anywhere to find, and are left with a plain placeholder rather than a stretched or wrong picture. Hovering a loaded thumbnail now grows it smoothly to a proper look at the artwork, and eases back down the moment the cursor leaves; a plain CSS `:hover` transform on the thumbnail itself, so it only fires over the artwork and never for the empty placeholder still waiting on a cover.
- **The album browser now takes the mickey out of MusicBrainz while it waits**: "Searching…" and "Loading albums…" were the only two boring status lines left in the place, so both now pick from a pool of two dozen digs at MusicBrainz's expense (disambiguations longer than the album, the rate limit, four identical MBIDs, that sort of thing) while the real lookup runs in the background. Same trick the live search panel and the Queue tab's aside already use, just aimed at a slower, more bureaucratic target this time.
- **The album list itself is now dramatically faster to load, for most artists**: `fetch_artist_albums` used to page through every raw *release* MusicBrainz has ever catalogued for an artist, every regional pressing, remaster and reissue included, at 100 per page with a mandatory one-second sleep between pages. A back catalogue with heavy fan documentation (bootleg-happy fanbases are particularly bad for this) could run to hundreds of raw releases behind a couple of dozen actual albums, so "load the list" meant several seconds of pure enforced waiting before a single title appeared. It now browses MusicBrainz's `release-group` endpoint instead, which is already deduplicated to one row per album, so most artists' entire discography arrives in a single request. The trade-off: a release-group carries no release ID of its own, so the specific pressing to download is now resolved lazily, one MusicBrainz request, only for the one album you actually open (`resolve_album_release`, backed by a new `GET /api/albums/release-group/{id}/tracks` route), rather than for the whole list up front, which would just relocate the rate limit instead of avoiding it. The Tracks-tab "download the whole album" handoff and the Bulk Import candidate flow now preselect by title rather than a release ID the list no longer carries, matching how the slow path already worked. Genuinely prolific/heavily-bootlegged artists (Radiohead's discography includes several hundred catalogued live recordings) will still see a few seconds and a couple of pages; everyone else should see the list appear in roughly one request.
- **Fixed a latent bug this same change would otherwise have shipped**: Watched Artists' "automatically add new albums" background job reads from the same `fetch_artist_albums` list and previously assumed a release ID was always present on every album, both when seeding an artist's existing catalogue as "already seen" (skipping the seed entirely once release IDs went missing, which would have made every album look brand new on the very next refresh, the exact back-catalogue avalanche the seeding step exists to prevent) and when queueing a genuinely new album for download (silently skipping it forever, since the download call requires a real release ID). Both spots now resolve a release ID on demand, via the same lazy resolver the interactive browser uses, only for the one album that actually needs one. Caught before release by tracing every consumer of the list's shape, not just the ones with a UI in front of them; covered by new tests in `tests/test_artist_albums.py`.
- **Amazon Music album links finally work**: paste `music.amazon.*/albums/<ASIN>` into Bulk Import's Fetch box and it now gets identified, matched against MusicBrainz behind the usual confidence gate, and downloaded into `Albums/Artist/Album/` with cover art, `.albuminfo` and track numbers, exactly as Spotify, Apple, YouTube Music, Beatport and Tidal already did. Amazon was the one that got away when album links landed in v4.0.3, and the note explaining why turned out to be wrong in an instructive way: it blamed the selectors, claiming album pages did not use the `<music-image-row>` components the playlist scraper reads. They do, twenty of them. They simply render as empty skeletons that never fill in, however long you wait, whatever cookies you carry, whichever user agent or regional host or deep-link form you try. No JSON carries the tracklist either, the app's own state object holds nothing but config, Amazon's retail pages 404 on these digital ASINs, and MusicBrainz has no ASIN coverage for them because its ASINs are physical CDs and vinyl. All of which is a long way of saying the page was never going to give up a tracklist. It does not have to: the album pipeline only ever needed an artist and an album name, because MusicBrainz provides the real tracklist once the record is matched. Driven by SeleniumBase's undetected mode rather than Playwright, and with the consent dialog actually dismissed, Amazon titles the page "Play <Album> by <Artist> on Amazon Music Unlimited", and that is the whole job done in one string. The rows still never populate; we no longer care. An album Amazon will not serve, whether delisted, region-locked or simply a wrong ASIN, leaves the generic site title behind, so a dud comes back as an honest failure rather than a confidently wrong record.

### Fixed
- **A failed Queue card that later succeeded on retry no longer contradicts itself**: retrying never resurrects a failed job, it opens a new Queue row for the next cycle and leaves the old failed one standing as a record of what happened. That's the correct call, but the failed card's own history panel was pulling the whole target's saga regardless of which job it belonged to, so an old card stuck permanently on "Failed" could show a *later* cycle's "completed" line right there under its own red status, looking for all the world like the software had lost the plot. Reported by Karl finding exactly this on a Soulseek rescue: "Failed", four cycles, and cycle 4 reading "completed" in the same breath. Each card's Journey and Cycle history is now scoped to its own cycle and earlier, so it only ever tells its own story, and the "last attempt" timestamp is its own rather than borrowed from a rescue that ran a week later. When a later cycle for the same track did go on to succeed, the old failed card now says so plainly with a "Later succeeded on retry" note that jumps straight to the completed entry, wherever it happens to be sitting in the Queue.
- **The scoring-rationale Copy button worked, provided you'd already clicked "Why this result?" first**: Copy only ever read from a cache that click filled in, so reaching for Copy cold did precisely nothing, no error, no toast, just silence. It now fetches the rationale itself regardless of what you clicked first, and says something either way, copied, or a plain "no rationale recorded" if there genuinely isn't one.
- **A YouTube Music album MusicBrainz cannot place now falls back to importing as a playlist, instead of just giving up**: `OLAK5uy_` links used to import fine as a flattened playlist, back before MusicGrabber knew what an album URL was. Once album-URL matching landed, an `OLAK5uy_` link that MusicBrainz could not confidently match, and offered no candidates for either, hit a dead end with "Couldn't confidently match that to a MusicBrainz album" and nowhere else to go, which is a worse result than doing nothing at all would have been. Spotify and Apple Music album links were never playlist URLs to begin with, so there was nothing to fall back to for them, and that stayed exactly as it was. YouTube's are dual-purpose, so an unmatched one now quietly retries down the ordinary playlist path instead of stopping to complain.
- **A manually searched track routed into a watched playlist now links to that playlist row the moment it's queued, not after it finishes downloading**: `POST /api/download` with a `playlist_name` has always routed the file into the right folder, but left `watched_playlist_tracks.job_id` empty until `_mark_watched_track_downloaded`'s after-the-fact artist/title healing caught up once the download completed. Anything that looked the track up by `job_id` in that gap found nothing. It links immediately now, the same way Retry and the watched-playlist panel's own download button already did.
- **Clearing Queue history now clears watched-playlist job links without breaking Replace**: `watched_playlist_tracks.job_id` used to point at deleted Queue rows forever because issue #83's Replace fallback depended on that stale value. Replace now addresses the durable playlist track itself using `(playlist_id, track_hash)`, while a database trigger nulls `job_id` whenever its job is deleted and the migration cleans up old dangling values. The track's downloaded state and resolved file path remain intact when history is cleared. Replace can still trash the file and rebuild the M3U after the Queue row has gone, only now it does so deliberately rather than treating a dangling pointer as an identity system.

## v4.0.4 (2026-08-30)

### Added
- **MP3Phoenix results can be previewed now, like every other source**: it was the one source with no way to audition a result, because the original reasoning was that spending a Cloudflare-cleared browser session on a hover is an impressively expensive tooltip, and that was fair enough. It now previews anyway, just carefully: only the opening megabyte is fetched, roughly 25 seconds at 320 kbps, and then MusicGrabber hangs up rather than pulling a whole file so somebody can decide it is the wrong mix. The bytes cannot go straight to the browser, because Cloudflare will not serve an `<audio>` element any more than it serves plain curl, so they come down through the same cleared session everything else uses and go back out from MusicGrabber's own address under a short-lived token, exactly as Monochrome previews already do. MP3 is quite happy being cut off mid-flow, so unlike Monochrome there is no ffmpeg in the way. Resolved previews stay cached in the browser for two minutes, so a second look at the same result costs the session nothing, and `MP3PHOENIX_PREVIEW_BYTES` and `TIMEOUT_MP3PHOENIX_PREVIEW` are there if you want it leaner still.
- **A "Re-download Missing Files" setting, for anyone whose library is organised by something else**: watched playlists and watched artists have always re-fetched a track whose file they can no longer find, on the sensible grounds that you probably deleted a duff rip and would like a better one. That logic falls apart the moment another tool owns your filenames. MusicBee, beets and friends move and rename files after MusicGrabber has finished with them, MusicGrabber then cannot find the track, downloads it again, the organiser tidies the new copy away, and the two of them settle into a lovely little duet that ends when the disk does. Worth stressing that a rename alone is enough; the file never has to leave your music folder for us to lose sight of it, because the check looks for `Artist - Title` in the places we put things, and `01 Title.flac` two folders over is not that. The new toggle lives in Settings under General and is on by default, so nothing changes unless you say so. Turn it off and a track downloaded once stays downloaded, however far its file has wandered. The Missing panel's per-track Retry is untouched, so you can still fetch one back deliberately; the point is that nothing fetches it back on your behalf, forever, at three in the morning. Watched playlist cards own up to the consequence rather than going quiet about it: any track in this state is counted on the card with a note explaining that it will not be chased and will not appear in the M3U, and the count clears itself the moment the files become findable again. Requested in issue #84, whose reporter had already worked out exactly what was happening and suggested both of the shapes this could take.
- **A Preview button on desktop, for people who would rather press one than hover**: desktop has always previewed by resting the mouse on a result for two seconds, while phones and tablets got an actual Preview button, on the grounds that hovering is not something you can do with a finger. Enough people have asked for that button on desktop as well, so there is now a toggle for it in Settings under General. Turn it on and every previewable result grows the same button strip touch devices get, and hovering stops starting previews altogether: nothing plays until you press the button, and what is playing keeps playing when the mouse wanders off, rather than dying the instant you move away. Off by default, so nobody's muscle memory gets rearranged without asking. The preference is stored in your browser rather than on the server, which means the desktop you browse on and the laptop you use on the sofa are free to disagree, and on a shared browser each account keeps its own answer.

### Fixed
- **"Create M3U" off now means off, rather than off-ish**: watched playlists with the option disabled were still having an `.m3u` created for them and appended to after every successful download, which is a bold reading of a tooltip that promises to leave an existing file well alone. Two code paths write that file: the full position-aware rebuild, which checked the setting properly, and a per-track append that fires on every completed download and checked nothing beyond whether a playlist had been named at all. The setting therefore worked perfectly, right up until something downloaded. Worse, the append tacks tracks on in the order they happen to finish, whereas the rebuild it was standing in for orders them by their upstream position, so an M3U that was never supposed to exist also drifted steadily out of the running order it would have had. The append now asks the same question the rebuild does: a playlist with the option off gets no file created and no existing file touched. Tracks still download into the playlist folder exactly as before, because where the audio lands was never anything to do with M3U generation. Reported in issue #82, whose reporter had already traced it to the offending function and spotted the ordering drift into the bargain.
- **Replace stops falling over when the original download job has been cleared**: pressing Replace on a watched playlist track could report "Failed to trash file" about a file that was sitting right there, perfectly writable, in a trash directory that worked fine when you moved it by hand. Nothing to do with the filesystem. Replace deletes through the job the track was downloaded by, and "Clear completed" bins job rows while leaving `watched_playlist_tracks.job_id` pointing hopefully at where one used to be, so the endpoint looked up a job that no longer existed and returned a 404. The frontend then translated that into a message about trashing, which is how you end up checking permissions that were never the problem. The lookup now falls back to the watched track's own `resolved_path`, which knew where the file was the whole time: the file gets trashed, the track goes back to missing, and Replace carries on to the search step as normal. A genuinely unknown job still 404s, as it should. The toast passes on what the backend actually said now, rather than inventing a filesystem fault to explain a missing database row. Reported in issue #83, complete with the database state that caused it.
- **Amazon playlists arrive in the order Amazon put them in**: watched Amazon Music playlists have been coming back sorted alphabetically by artist, which is a lovely way to open a chart playlist with whoever happens to be called Aaron. The scraper collected rows into sets, which have no order at all, and then ran the result through `sorted()`, which gave them an order nobody asked for; everything downstream was faithfully preserving that. Rows are now keyed on the position Amazon's own virtualised list gives them, which is why this is not simply a matter of swapping the sets for lists: the page recycles rows as you scroll, MusicGrabber crawls the playlist twice to catch the ones that got away, and anything found on the second pass would otherwise be dumped at the bottom of the playlist rather than put back where it belongs. The position is the list's own, not the screen's, so it survives scrolling, recycling and both passes; verified against a sixty-track chart playlist at a viewport small enough to force constant recycling, which came back in exact order. Tracks found only in Amazon's JSON responses, a fallback that contributes nothing on a normal playlist page, still get appended in the order they were discovered rather than thrown away. Reported in issue #81, whose reporter had already found the offending line. Existing watched playlists sort themselves out on their next refresh.
- **Explicit tracks stop being searched for under a title that does not exist**: Amazon renders the explicit badge as its own line inside the title cell, so "petal" came through as "petal E", "Ain't In LA" as "Ain't In LA E", and so on for a good fifth of the average chart playlist. MusicGrabber then went looking for a song of that name, with the results you would expect. The badge is now dropped, and only when it is the whole trailing line, so anything actually called "E85" or "Vitamin E" keeps its name.
- **Preview requests no longer race each other or multiply while loading**: starting another preview now cancels the browser request already in flight, stale replies cannot take the player back over, and pressing the same loading button again cancels it instead of queueing another provider fetch. The two-minute cache is keyed by source and source URL as well as the visible result ID, so unrelated providers cannot borrow one another's audio by coincidence.
- **A bad MP3Phoenix preview can no longer put the source into a ten-minute sulk for everyone**: preview accepts only the `/getmp3/...` HTTPS media links search actually emits, and stale or caller-invented preview tokens fail locally without incrementing the shared search/download circuit breaker.
- **The integration test client no longer replays mutations after an ambiguous disconnect**: safe GET/HEAD/OPTIONS requests retain connection retries, while POST, PUT, PATCH and DELETE now fail visibly when the server has received the request but loses its reply. That avoids creating duplicate downloads or hiding response-after-commit bugs during a test run.
- **Album downloads now tag a year, and every track agrees on the same one**: album tracks were each going off to MusicBrainz on their own after landing, which meant each one formed its own opinion about which release it came from, and since the scorer has a deliberate soft spot for earlier pressings, a 2015 remaster could come back wearing 1973. Tracks whose lookup found nothing at all got no year whatsoever, so a single album could arrive with three different years and a couple of blanks, which does interesting things to how Navidrome and Plex decide what belongs together. The year of the release you actually picked is now taken when the album is queued, read out of the very same MusicBrainz response the tracklist already arrives in, so it costs not one extra HTTP call, then stored with the import and stamped on every track. It is the date of that specific pressing, so a remaster admits to being a remaster rather than passing itself off as the original. The per-track guess stays on as a fallback for anything queued before this landed. The year goes into the `.albuminfo` sidecar too. Albums already sitting on disk are left exactly as they are; this is for new downloads.
- **YouTube previews play again, by hover and by button alike**: the browser was being handed a googlevideo URL it is no longer allowed to stream. yt-dlp resolves YouTube through one of several "player clients", and the binary baked into the image had settled on ANDROID_VR, whose URLs now cap a single response at roughly a megabyte: ask for the first kilobyte and you get a cheerful 206, ask for the whole four-megabyte track, which is precisely what an `<audio>` element does, and you get a 403. MusicGrabber never saw any of it, because the part that failed happened between the browser and Google; our own preview endpoint returned 200 every single time, and the only symptom was silence, a card that gave up, and a fresh resolve on every retry because the failed URL was correctly evicted from the cache. Current yt-dlp resolves via a client whose URLs serve the whole file, so the fix is simply to be running a current yt-dlp: the container now updates it at boot, bounded to 45 seconds so a sulking network delays the start rather than preventing it, never fatal, and skippable with `YTDLP_AUTO_UPDATE=false` if you would rather pin whatever shipped. The image had always asked for the latest yt-dlp at build time; Docker had simply been reusing a cached layer from July, which is a wonderful way to ship a five-week-old binary while believing you have done no such thing. Downloads were unaffected throughout, since yt-dlp chunks its own requests, as did Monochrome previews, which are served from MusicGrabber's own address rather than Google's.
- **A slow preview no longer times out at exactly the wrong moment**: yt-dlp solves YouTube's player challenge through Deno, which takes a couple of seconds when the answer is cached and a good deal longer when YouTube has just shipped a new player. The preview timeout was 15 seconds, which sat precisely on that boundary and turned an ordinary slow resolve into a 504. It is now 30, and configurable via `TIMEOUT_YTDLP_PREVIEW`.
- **The test suite stopped failing at random**: MusicGrabber's uvicorn closes an idle keep-alive connection after five seconds, and the shared test client was a plain `requests` session with no retry adapter on it. urllib3 spots a socket that has already died and quietly opens a fresh one, so the ordinary case was never the problem; the problem was the server's hang-up crossing in flight with our send, which comes back as `ConnectionError(RemoteDisconnected)` and cannot be dodged. It took out roughly one slow run in two, always in the album-routing tests (they wait out a real download and then make a request, which is precisely the wrong moment) and never the same test twice, which is a wonderful way to waste an afternoon convincing yourself you have broken album routing. Safe read-only requests now retry a connection that died without answering. Mutations do not: a dropped response cannot prove whether the server committed the work, so POST, PUT, PATCH and DELETE fail visibly rather than risk doing it twice. It pointedly does *not* retry on an HTTP status either: a 500 is a finding, not a blip.

### Changed
- **MP3Phoenix is no longer labelled experimental**: it works, so the word has come off the Settings toggle, the README and the source registry. It stays off by default, exactly as it was, on the grounds that briefly launching Chrome for Cloudflare clearance is not something an upgrade should spring on an install that never asked for it. Soulseek has managed off-by-default for years without anyone calling it experimental.
- **The Preview button now admits what it is up to**: resolving a YouTube URL takes a few seconds, and a button that simply sits there looking pressed is indistinguishable from one that does nothing, so people press it again. It now reads "Loading..." and pulses while the URL is being fetched, "Stop" while the track is playing, and goes back to "Preview" afterwards. A preview that runs all the way to the end also clears the card properly, rather than leaving it looking like it is still playing half an hour later.

No login, no cookies, no headless browser. Reported by console1982, who did the legwork on finding the paginated endpoint.

A 404 there now just tidies the row away with an "Already handled elsewhere" toast instead of reporting a failure that never happened.

The early local/Navidrome/Lidarr check now short-circuits the transfer; the existing post-download check remains as a safety net when embedded tags correct a dubious path-derived artist.

Handy for the failed attempts, less so for the successful ones, since a genuine swap-in-place vanished just as thoroughly as a rejected one, leaving nothing in the Queue and nothing to look back on. A completed upgrade now stays in the Queue like any other finished download (tagged with an UPGRADE badge so it doesn't get mistaken for a fresh acquisition), pointed at wherever the swapped-in file actually ended up. ## v4.0.2 (2026-08-16)

### Fixed
- **Soulseek track upgrades no longer fail after a successful download**: the upgrade worker's Soulseek call was missing the duplicate-check bypass its own sibling call (for every other source) already had, so it dutifully found the file being replaced, declared the download "already exists", and threw the freshly-fetched replacement away, reporting "Download failed or produced no file" despite Soulseek having done its job perfectly. It now skips that check the same way the rest of the upgrade path always has.
- **Opus upgrades were being rejected as "not actually better" even when they very much were**: Ogg Opus doesn't declare a per-stream bitrate the way MP3 does, and neither ffprobe nor mutagen can read one back out, so a lossless-sourced Opus conversion picked up a quality label with no number in it at all ("OPUS (from FLAC)"), and the tier check, finding nothing to compare, defaulted it to the lowest possible tier alongside every other unnumbered Opus file in the library. Since we already know exactly what bitrate we told ffmpeg to encode at, that number now gets stamped into the label instead of leaving it to guesswork ffprobe can't do. New downloads and upgrades are unaffected either way; existing library files keep whatever label they already have until they're next replaced.
- **Watched Upgrades no longer lists files it already knows it can't upgrade**: a candidate stays on the page forever once searched, even after that search turns up nothing, so the list slowly filled up with permanent "No better copy found" dead ends. Those now drop out once the search comes home empty, and reappear on their own if the file itself later changes.

## v4.0.1 - Fix of the Phoenix (2026-08-16)

### Added
- **Long DJ mixes and "CD1/CD2"-style compilation uploads can now be split into proper tracks instead of downloaded as one 90-minute blob**: paste a single YouTube video into the Bulk Import Fetch box and, if it runs over 12 minutes, MusicGrabber checks whether it looks like a compilation before offering to cut it up. It never guesses a track boundary: it prefers YouTube's own chapters when the uploader bothered to add them, then a hand-typed cue sheet sitting in the video's own description (surprisingly the most common spot in the wild, and the timestamps YouTube auto-links there are not the same thing as real chapters, a distinction that cost some debugging), then one hunted out of the comments (the winning comment is whichever one has the most timestamp-shaped lines, so an offhand "great fade at 16:55" doesn't get mistaken for the real thing), and otherwise hands you an empty table to fill in yourself, or a box to paste your own cue sheet into. Either way you get an editable preview, start/end/title/artist per row, before a single byte downloads. Confirming it downloads the audio once, cuts each segment with ffmpeg, runs it through the same integrity check every other download gets, and tags it directly from what's in the table (no automatic MusicBrainz guessing against chapter titles like "Track 3 (Extended Mix)"), landing the lot in `Albums/Album Artist/Video Title/` with cover art pulled from the video thumbnail. Album Artist defaults to "Various Artists" unless every row agrees on one. This only ever triggers from the Fetch box itself, a plain search or a pasted "Artist - Title" list is left well alone, and a video only qualifies when it isn't already a genuine curated playlist; YouTube tacks its own auto-generated "radio mix" list onto ordinary watch page URLs, which very nearly got mistaken for one.
- **Pasting a link into the ordinary Search box now goes to Bulk Import instead of being searched for as if it were a song title**: a Spotify playlist URL, a YouTube link, and so on used to just sit there being an unsearchable string. It's now handed straight to the box on Bulk Import that already knows what to do with it, playlist, album, or long-form video, tab switch and all, without the user having to notice they typed it in the wrong place.

### Security

- **Download and preview URLs must now prove they belong to the source that claims them**: both endpoints took a `source` and a `source_url` from the browser and went and fetched it, without ever checking the two had met. Since the caller writes both, an authenticated user could declare "soundcloud" and hand over `http://127.0.0.1:8080/`, the NAS admin panel next door on the Docker network, or a cloud metadata endpoint, and MusicGrabber would dutifully fetch it from inside the container. Every URL-backed source now has a hostname allowlist, matched by exact host or subdomain, so `soundcloud.com.evil.tld` gets the door as firmly as `169.254.169.254` does. Monochrome is checked on its private scheme instead, since it never hands a fetchable URL to anything. Stored rescue candidates are re-checked before they are replayed, and the download worker refuses anything that matches no known source rather than shrugging and passing it to yt-dlp.
- **Custom playlist folders can no longer wander out of the music directory**: "subdir" was doing a lot of trusting in that field name. `../../tmp/escape` and `/tmp/absolute` were both joined onto the music root and used as-is, and the value was copied into the durable acquisition destination so it survived rescue cycles too. Absolute paths and `..` hops are now refused at the API with a clear message, and every path is re-checked for containment immediately before use, with both sides resolved so a symlink cannot talk its way past a lexical prefix check. The same guard covers the per-user Singles, Playlists and Albums folder settings, which were quietly wide open in exactly the same way.
- **The trash bin is no longer one shared heap**: `get_trash_dir()` accepted a user ID and then ignored it, so on a multi-user install anyone with an account could list, play, restore or permanently delete anyone else's binned music. Restore was the cheekiest of the lot, since it dropped the other user's file into your library. Each account now gets its own bin. Single-user installs are untouched, and anything already sitting in the old shared bin is moved into the first admin's on startup rather than being left on disk but invisible to everyone, which would look a great deal like MusicGrabber having eaten it.
- **Watched Artists now checks the right user's library**: the refresh loaded the watch's owner and then left them out of all three duplicate checks, so on a multi-user box it could miss files in the correct library, find them in the wrong one, store somebody else's absolute path, or mark a track downloaded that its owner cannot actually reach.
- **Soulseek no longer deletes a stranger's file because it had the right name**: when the exact completed-transfer path could not be found, the fallback searched the peer folder and then every download root for the first file with a matching basename, which on a network awash with `01 - Intro.flac` is optimistic. With move mode on, whichever unlucky match it picked was then removed from disk. The expected byte count must now agree as well, and if two files still both fit, it refuses to guess rather than binning one of them on a coin flip.
- **Force Accept now checks whose job it is before it touches anything**: it set the skip flag and deleted the job's mismatch evidence using only the job ID, and left the ownership check to the retry it delegated to afterwards. Someone who learned another eight-character ID could not complete the retry, but could certainly wreck the record on the way through. It resolves the job first now, and a job outside your scope gets a 404 and an untouched database.

### Fixed

- **Append-playlist unresolved counts now include retained history**: the card used to count only tracks still present upstream, even though append mode deliberately keeps everything seen before. Downloaded historical rows are now checked too when the leave-alone policy applies; missing ones join the warning count but are never automatically queued again.
- **Restoring a rejected download now repairs its Queue row**: Restore moved the file back into the library but left its Queue entry failed, which was a rather mixed message. The matching failed job now becomes completed and clears its old error, including its watched-playlist or artist record. Exact saved paths are used where available; older rows fall back only when one artist/title match is unambiguous.
- **The play buttons in the Queue and the Trash play something again**: every one of them answered with "Could not play file", and the file was entirely innocent. An `<audio>` element cannot be persuaded to send an `Authorization` header, so the moment the browser fetched the stream URL it arrived with no session token, collected a 401, and the audio element reported the only thing it knows how to report, which is that it could not decode the source. The middleware already had this exact problem solved twice over, once for the download button and once for Monochrome previews; playback simply never got its own key cut. It has one now: a short-lived, reusable, user-bound token that rides in the URL, works with the range requests a seeking player makes, and is accepted on the two playback endpoints and nowhere else. It has been broken on every multi-user install since play buttons arrived in v2.5.3; single-user installs never noticed, because they skip authentication entirely and the whole thing worked by accident.
- **Various Artists albums stopped hunting for songs by "Various Artists"**: the tracklist fetch kept title, position, ISRC and recording ID but dropped the one thing a compilation exists to vary, so every track on a soundtrack went looking for a performer who has never released anything. When ISRC resolution missed, the fallback search used that fiction and album mode's strict artist gate then rejected the genuine recording when it turned up. Track and recording artist credits are now kept and used for searching and matching, while the sleeve credit stays on as the album artist where it belongs.
- **Double-clicking an album or a retry no longer queues it twice**: both checked whether something was already running and then created it a moment later, which is plenty of time for a second click to pass the same check. Album destinations are now guarded by a uniqueness rule in the database itself, so the second one loses and is told an import is already in progress; rescue admission takes the write lock before it looks, and claims its cycle number inside the same transaction, so a rescue that loses the race no longer burns a cycle on its way out. Cycle allocation is a single atomic statement rather than a read, an add and a write with a gap in the middle.
- **Serving, retagging, moving and deleting a file now check it is still one of yours**: the stored path was trusted on the strength of being absolute and existing, which says nothing about whether it still lives in your library. A track replaced by a symlink would have led a delete straight out of it. All five of those paths now share one check: a real regular file, an extension we actually deal in, and inside the current user's music root, or we fall back to searching the library properly.
- **A large library rebuild will not fall over on itself**: it minted every synthetic row ID from eight hex characters, a 32-bit space where a collision becomes a coin toss somewhere around fifty thousand rows, and one collision aborts the entire batch. Those rows now carry full UUIDs. Nobody types them, so the extra characters cost nothing.
- **Monochrome playlist share links (`monochrome.tf/playlist/...`) fetch tracks again**: they went through hifi-api, which has since gone the way of the Qobuz proxies, Tidal itself is now turning away its OAuth client with a 403. Turns out that was never necessary: a Monochrome playlist share is a Tidal playlist UUID wearing Monochrome's hostname, and MusicGrabber already scrapes plain `tidal.com` playlist links straight from Tidal's own embed player, no hifi-api involved. Monochrome share links now go through the exact same route. The public hifi-api instances also no longer have a default URL to fall back to, since both known ones are confirmed dead, so search stops spending a couple of guaranteed-failed round trips hunting for a Tidal top-up on every query. Anyone self-hosting their own hifi-api can still point `MONOCHROME_HIFI_API_URL` at it.

### Changed

- **The retired Qobuz proxy layer has left the building**: Monochrome no longer probes, retries, cools down, configures, or waits for public proxy endpoints whose credentials and API have expired. Browser-authenticated Monochrome playback is now the first download route, followed by direct qbdlx and Tidal fallbacks. Qobuz catalogue checks use the direct qbdlx client, and the obsolete setting is removed automatically by database migration v13.
- **Settings can now prove Monochrome works, rather than politely assuming it does**: a new "Test Downloads" button under Monochrome walks the entire download path exactly as a real job would; it reaches a hifi-api, searches for a known track, tries each leg of the resolution ladder in turn, downloads the actual FLAC, decrypts it where Monochrome served it encrypted, and ffprobes the bytes that arrived, before deleting the lot. It then reports every step with a pass, warn, skip or fail, so a broken install stops being "Monochrome doesn't work" and starts being "Chromium could not start" on a specific line. Routes that were deliberately switched off are marked skipped rather than blamed, the raw error text is shown so it can be pasted into a bug report, and the usual suspects (a container short on shared memory, a missing Chrome, a Turnstile timeout, a dry qbdlx token pool, DNS gone walkabout) get a plain-English likely-cause line underneath. Takes around ten seconds when all is well, a minute or two if Chrome has to warm up first, and politely refuses to run twice at once, since one browser session and one 28 MB download is quite enough.
- **Monochrome previews are back, and downloads reach its own infrastructure sooner**: the browser-authenticated unified-playback leg used to serve downloads only, on the sound reasoning that nobody wants Chrome booting because they hovered a play button. Nobody still does: the browser session is now warmed once in the background at startup, so by the time anyone hovers anything it is already sitting there ready. A hover gets an answer in under a second, or steps straight on to the next leg if the session is busy with a download; it never queues behind one and never starts Chrome itself. The warm-up only happens when Monochrome is actually an enabled source with the browser leg switched on, because heating a browser for a source nobody searches is a very elaborate way to warm a container. The leg has also moved up the download ladder, ahead of qbdlx's shared Qobuz tokens rather than behind them; measured on the day, 8 of 25 of those tokens were usable, so trying Monochrome's own infrastructure first, which needs no token at all, means fewer downloads waiting on that coin flip. qbdlx remains the fallback for when even that comes up empty. (Investigated and ruled out: reusing MP3Phoenix's SeleniumBase-then-curl_cffi trick here. Monochrome's Turnstile JWT carries an IP and a fingerprint claim and is rejected even when replayed seconds later from the very same address, so it looks genuinely bound to the browser session that earned it.)
- **Fixed previews failing outright whenever every other Monochrome leg was down**: which, given qbdlx's token pool keeps thinning, is precisely when a preview needed the browser most. The gate meant to stop a hover cold-starting Chrome only let previews use a session that was already running, and nothing ever started one, so the condition could never be met and the hover fell through to a 67-second walk past 25 dead qbdlx tokens before giving up with a 500. Warming at startup gives the gate something to actually find.
- **Monochrome hover previews now actually play, rather than merely claiming to**: Monochrome's unified playback hands back CENC-encrypted FLAC-in-MP4 at every quality tier it offers, and an `<audio>` element will stare at that blankly no matter how successful the request looked. Downloads have always decrypted with ffmpeg and an in-memory key; previews now get the same treatment at a much smaller scale, decoding the opening thirty seconds to a 192 kbps MP3 that MusicGrabber serves itself. Roughly two seconds from hover to sound, and cached for ten minutes afterwards. The snippet is reachable only through a full uuid4 token that resolves back to whoever asked for the preview, since an audio element cannot carry an auth header and the alternative was leaving a door open and hoping. Snippets are capped, aged out, and deleted with their files. Sources returning ordinary playable audio, such as Tidal, still pass straight through untouched.
- **Fixed the search box's clear button being sat on by the Search button**: the clear cross was pinned at a fixed distance from the right edge, measured for the word "Search". The moment the button started saying "Searching…" it grew wider, spread leftwards, and parked itself directly on top of the cross. The button now keeps one width whatever it happens to be saying.
- **The Bulk Import Fetch button no longer writes over whatever you just pasted**: same species of bug as the Search clear button above, on the box next door. "Hunting for a cue sheet…" and "Scrolling playlist (large lists take a minute)..." are a good deal longer than "Fetch", and the button was never told to stop growing, so on a long enough label it sailed clean over the URL sitting underneath it. It's capped and ellipsised now rather than left to sprawl.
- **The long-form split panel no longer sits flush against the Fetch box above it**: it borrowed its styling from a warning banner that carries no top margin, since nothing else built on that class ever needed one. It has its own margin now, so there's a bit of daylight between the two.

## v4.0.0 - Rise of the Phoenix (2026-08-12)

- **Rise of the Phoenix**: MP3Phoenix returns as an experimental source, disabled by default. SeleniumBase briefly clears Cloudflare, then `curl_cffi` reuses those cookies and the exact user-agent with Chrome's network fingerprint for efficient AJAX searches and streamed MP3 delivery. The session lives for at most an hour, but any challenge response refreshes it immediately and retries once. The image now runs under `tini`, which reaps each short-lived Chrome cleanly instead of collecting browser zombies. Results rejoin the normal relevance and quality ranking at the declared 320 kbps tier, and completed bytes still face the ordinary integrity, duration, metadata, conversion, duplicate, and fallback checks. Three consecutive failures put the source back in its box for ten minutes, because endlessly launching Chrome at a locked door is not resilience.
- **The Phoenix got a once-over the day after it landed**: a review turned up its cooldown resetting itself on every call it made while parked, so it could stay disabled forever instead of retrying after ten minutes; a browser bootstrap timeout shorter than the browser's own Cloudflare wait, which risked killing a slow-but-succeeding session mid-clearance; and its ~10-minute health check launching a full Chrome instance just to say "yes". All three are fixed, alongside a genuinely broken bit: the frontend never actually sent MP3Phoenix downloads their source URL, so every click-to-download 400'd. Search-result cards also stopped offering a Preview button MP3Phoenix can't serve, and its HTML scraper now bails out and asks again rather than risk mis-pairing a title with someone else's download link.
- Fixed Album mode and Watched Artists album acquisitions incorrectly reporting fetched tracks as already in the library, including Soulseek's post-download duplicate gate.
- **Fixed Monochrome downloads occasionally getting tagged with someone's bootleg**: MusicBrainz can attach one ISRC to both a studio recording and one of its many live bootlegs, and the ISRC lookup used for Monochrome tags was taking whichever the API happened to list first. That's how a perfectly good FLAC of Radiohead's "Creep" ended up filed under "1998-06-14: Tibetan Freedom Concert, RFK, Washington DC, USA" with no year to show for it. It now scores every candidate recording the same way the ordinary title-search lookup already does (release count, live/remix penalties, the lot) and picks the best one, rather than trusting list order.
- Fixed the Bulk Import album browser's disclaimer note touching the search box above it, and, while we were in there, noticed it was rendering a second identical copy of itself and quietly showing up twice. It now shows up once, with a gap either side like a civilised element should.
- **Fixed the tag editor's "Guess Again" occasionally guessing a bootleg**: it searched MusicBrainz by text alone and sorted purely by raw relevance, with none of the alt-take protection ordinary downloads already carry. Re-guessing The Beatles' "Let It Be" could hand back a rehearsal take filed on the "Artifacts II" box set, complete with 1994 and track 11 of 23. It now shares the same canonicity-scored recording picker as an ordinary download, and tries fingerprinting the actual file with AcoustID first when it is available, so a re-guess is grounded in what the audio actually is rather than whatever a text search happened to match.
- The Queue's live summary line now picks from a small pool of quips per state instead of reciting the same two lines forever. Apologies to any "Tiny hammers" loyalists; there is more where that came from.

The artist-centred restructure, in which MusicGrabber stops organising itself around what it downloads and starts organising itself around who made it. Monochrome's lossless downloads also came back from the dead, and a rather nasty database bug wandered in and got fixed while we waited.

### Changed
- **The Albums tab has been retired, and the navigation now makes rather more sense**: the tab bar reads Tracks, Bulk Import, Artists, Watched, Queue, Stats, Settings. Albums was never really a place, it was a way of finding things, so its artist browsing, "do I already own this?" checks and release-download mechanics have moved into Bulk Import and the new Artists tab rather than being deleted. Both surfaces run the same album browser: one component, mounted twice, so there is no second copy quietly drifting out of step with the first. Watched has slimmed down to Watched Playlists and Watched Upgrades, which is all anyone ever went there for; the read-only Audio Provenance Audit stays put alongside them. Nothing about the fast search-tap-done single-track workflow on Tracks has changed, because that is the whole point of the thing and moving it would be daft.
- **Watched Artists has grown up and moved out, into a proper Artists tab**: same MusicBrainz candidate picker, same "watch future singles from this date" behaviour, same intervals and per-artist controls, now with room to breathe.
- **Picking an artist no longer commits you to anything**: find the artist once, then choose what you actually want from them. Follow for Singles behaves exactly as it always has. Follow for Albums lays out the whole discography with tick boxes, so you can grab five records in one go instead of picking one, waiting, going back, picking the next, and it carries its own opt-in for future releases. Download an Album does precisely that and remembers nothing about it afterwards. The old order of operations had you follow an artist for singles first and only then discover, behind a button on their card, that albums existed at all; the choice belongs at the front, not buried two clicks into a decision you have already made.
- **Singles and albums are now independent switches on the same artist**: follow someone for singles today, add albums next week, or take the albums and leave the singles entirely. An albums-only follow does not go anywhere near their singles, which for a prolific artist is the difference between a few albums and four hundred B-sides, remixes and radio edits. Every artist you already follow keeps watching singles exactly as before, because that is what following them has always meant. The one thing you cannot do is switch both off; an artist following nothing at all would just sit there indefinitely doing sod all, so that politely points you at Delete instead. Albums you tick by hand are recorded as dealt with, so the automatic side never cheerfully queues them a second time.

### Added
- **A maintenance centre which shows its workings before touching the database**: Settings now previews orphan watched imports, Queue history by state, and exact indexed paths. Admins can remove orphan imports, clear selected history states, reconcile files removed outside MusicGrabber, or clean and rebuild the path index from configured library folders. Every action requires confirmation and none deletes or moves audio; the broom has been firmly told where the china lives.
- **An honest last chance for YouTube playlist tracks**: an off-by-default setting retains each playlist entry's original video ID and uses that exact video only after every confident alternative has failed. The Queue says when this happened, and the stored fallback survives edited or reordered import previews without attaching one song's video to another.
- **Failed automatic downloads now have an actual rescue journey**: **Retry next option** appends a fresh Queue row and numbered acquisition cycle instead of rewriting the failed row, tries saved untried candidates before searching again, and remains inside the target's original source allowlist. **Choose version** opens the runners-up already saved during automatic search, lets you preview and explicitly choose one (including a previously attempted version), and can refresh only those allowed sources. Expected artist/title, playlist or album destination, conversion choice, source exclusions, and watched-row linkage survive both paths.
- **Auto-added albums get another go after a queueing wobble**: a failed hand-off no longer makes the release permanently known and therefore permanently ignored. The album row records its attempt count, last attempt and error, then retries once on the next owning artist check; successfully queued and deliberately seeded releases remain terminal.
- **Automatic downloads now remember the whole hunt instead of only the horse that crossed the line**: Bulk Import, Watched Playlists, watched artists, and album acquisitions now keep one durable target across later Queue jobs and cron refreshes. Each refresh opens a numbered, bounded cycle; every candidate leg records its service, candidate, quality claim, time, result, and error; and the expanded Queue card shows the latest twenty attempts plus total cycle/attempt counts. Candidate selection gates recording identity first, then walks known lossless results towards progressively worse lossy formats inside the user's strict source allowlist. A preferred source breaks ties within a quality tier rather than promoting its MP3 over an available confident FLAC. One failed service gets one candidate per cycle before the next service has a go, while Soulseek may try another peer for the same recording. If the lot fail, the next owning cron refresh starts a fresh cycle because today's missing track may be tomorrow's perfectly ordinary result. Manual single-result selections remain pinned to the service the person actually chose—quietly replacing a deliberate pick is not automation, it is cheek. Existing failed imports are not backfilled or awakened during migration, and every old Queue row remains where it was.
- **Bulk imports have a real Cancel button**: cancellation is now a lifecycle rather than another spelling of Clear Queue. Each import owns at most one active file; that file is allowed to finish, untouched tracks and queued jobs are marked cancelled, completed library files stay put, and every Queue row remains as history. Deleting a watched playlist requests the same cancellation in the same database transaction before removing the playlist, so a refresh cannot carry on scheduling tracks for something that no longer exists.
- **Search concurrency is explicit and conservative**: Settings → Search Sources now permits one to five simultaneous searches per provider, defaulting to one. Interactive and automatic work share the same bounded semaphore. Download concurrency remains an internal limit rather than a prominent “please get me banned” slider.
- **The singles start date is finally something you can choose, and change**: follow an artist for albums only and their row still quietly carries a `from_date`, set to whichever day you happened to follow them. Switch Singles on a fortnight later and that forgotten date is what decides how much of their back catalogue turns up, and nothing in the interface ever offered to let you say otherwise. Flipping the Singles toggle now opens a small prompt asking which date to watch from, defaulting to today, and **nothing is saved until you confirm it**: cancel and the toggle goes back where it was, having sent absolutely nothing. Once singles are on, the date lives on the card as an ordinary editable field, so you can wind it back to pick up last year's releases or push it forward for a bit of peace. The API has always accepted `from_date` on update; it was simply that nobody ever sent one. It now also refuses anything that is not a real `YYYY-MM-DD` date, because that value gets compared against MusicBrainz release dates as a plain string, where "last Tuesday" sorts somewhere daft and silently filters out either everything or nothing.
- **Artists can now hoover up new albums automatically, if you ask nicely**: an opt-in "automatically add new albums" toggle per followed artist. The important bit, and the reason this took some care: switching it on does **not** download the back catalogue. Flipping the switch records everything the artist has already released as "seen, thanks" and queues precisely none of it; only albums that turn up afterwards get collected. Anything else would turn a single click into a fortnight of NAS-filling, and a toggle you cannot trust is a toggle nobody ticks. Album arrivals reuse the same MusicBrainz filtering the singles watcher already uses, so live records, compilations, soundtracks, DJ mixes, demos and remix collections stay out of it. Remasters, reissues and deluxe editions are deliberately *not* filtered; they are occasionally noise, but they are also frequently the thing you actually wanted, and guessing wrong in either direction is worse than letting you look. Albums are remembered by their MusicBrainz release-group, so an album stays the same album even when MusicBrainz catalogues an earlier pressing and changes its mind about which release represents it.
- **Album browsing without the commitment**: you can search any artist, browse their albums and download one without following them at all. Not everything needs a subscription.
- **The album list tells you what you already own**: browsing a discography now marks the records already sitting in your library, so a tick-box list cannot talk you into downloading your own collection back to yourself. They stay tickable rather than disabled, mind, because re-acquiring something you only own as a dodgy 128k rip is an entirely reasonable ambition. The check is pure filesystem and adds no MusicBrainz traffic at all.
- **Bulk Import is now the front door for acquiring almost anything**: one box that works out what you gave it. Playlist URLs, raw "Artist - Title" lists and MusicBrainz release links all behave exactly as before; Spotify and Apple Music **album** URLs are new, as is simply typing a name. Every input recognised as an album is routed through the album pipeline, so it lands in `Albums/Artist/Album/` with artwork, an `.albuminfo` sidecar and real track numbers, instead of being flattened into a pile of anonymous singles. That flattening was the actual bug here; an album is not a playlist that happens to rhyme.
- **Album search that does not demand an artist first**: type "Trainspotting", or "Now That's What I Call Music 42", and you get sensible answers. Soundtracks, compilations and Various Artists releases are first-class citizens rather than awkward exceptions, and results are labelled with what they actually are (Soundtrack, Compilation, Live) so a tribute album cannot pass itself off as the real thing. Searching stays quick by not resolving a release for the nine albums you are about to ignore; that work happens for the one you pick.
- **A confidence gate on album matching, because guessing wrong is expensive**: matching "some album name off Spotify" to a MusicBrainz release is fuzzy work, and a wrong answer does not cost you one duff track, it costs you a whole duff album. Anything below the confidence bar stops and asks which one you meant, and even a confident match shows you what is about to be queued before a single byte moves. YouTube, Amazon, Beatport and Monochrome album URLs are honestly unsupported rather than half-supported; there is no album-URL contract for them yet, and pretending otherwise helps nobody.

- **Monochrome serves real FLACs again, by asking the way its own web player does**: Monochrome moved unified playback behind a Cloudflare Turnstile exchange, which left MusicGrabber's HTTP-only legs politely locked out and the Qobuz proxies unable to help. There is now an optional fallback that opens a short-lived, headed Chrome session under Xvfb via SeleniumBase, completes the same Turnstile check a human visitor gets, and resolves one authorised audio resource. Only the small playback JSON request happens in the browser, because Monochrome ties the short-lived token to the session that earned it; the audio itself still downloads through MusicGrabber's ordinary HTTP client, which is where all the sensible progress and integrity handling already lives. Some lossless resources arrive as standard CENC AES-CTR FLAC-in-MP4, so the authorised key is kept in memory only and handed to ffmpeg, which decrypts and remuxes to a clean FLAC before anything else touches the file. The browser is a genuine last-ditch measure, not a habit: it is never launched for previews (nobody wants Chrome booting because they hovered a play button), it runs one session at a time, and it can be switched off in Settings under Monochrome or with `MONOCHROME_BROWSER_FALLBACK_ENABLED=false`. Resolution takes a few tens of seconds per track, which is the price of admission and still infinitely quicker than not getting the track at all. The image now carries Google Chrome on amd64 and Debian Chromium on ARM, so it has grown; the ARM route works but is fussier about browser and driver versions, as ARM tends to be.

- **Bulk imports now get looked after when their worker dies**: an import runs in a daemon thread, so a crash or a container restart left the row saying "processing" with nobody behind it, permanently. The local test instance had accumulated 36 of them, the oldest insisting it had been busy since January, and between them they held every search source's admission slot often enough to make searches fail for no visible reason. Imports now carry a progress heartbeat, so a stalled one is spotted by its silence rather than by a stopwatch; a fourteen-hundred-track import is entitled to take all afternoon. Anything quiet for an hour is picked back up where it left off, with tracks caught mid-search returned to the queue rather than blamed for our crash. Restarts are handled at boot instead, since nothing survives one and making an orphan sit out the timeout helps nobody. Three revivals is the limit, after which the import is failed and says so; an import that dies at the same track forever is a slow-motion infinite loop, not a retry. Imports older than a week are never resurrected, because downloading a pile of music you stopped waiting for in spring is not a favour. Neither is one belonging to a watched playlist you have since deleted, which turned out to be 32 of the 36.

- **Soulseek search results now say something useful about themselves**: a result used to be a title, a Soulseek username, a format badge and a duration, which between them told you almost nothing about whether it was the right file. Each card now carries the artist, the album and its year, the file size, the bitrate, the album's cover art, and how closely the shared file's path matches what you actually searched for, shown as a percentage down the right-hand side. Nearly all of it was already in the search response and simply being thrown away: slskd hands over the size, duration and bitrate per file, the album and year are sitting in the shared file's own path, and the match confidence was already being calculated to decide which results to keep before being discarded. Cover art is the one genuine addition, looked up once per album rather than once per result and cached for the session, so a page of twenty results from the same record costs exactly one lookup. Only Soulseek shows a match percentage, because only Soulseek has an honest number to put there; inventing one for the other sources would look consistent and mean nothing. The bitrate for a lossless file is worked out from its size and duration rather than declared, which is the more useful figure anyway: a "24bit/96kHz" FLAC quietly running at 900 kbps is an upscale, and now it says so.
- **Soulseek downloads can be moved rather than copied, if you ask**: an opt-in "Move completed downloads" toggle under Settings → Soulseek, off by default. MusicGrabber has always copied the finished file out of slskd's completed folder and left the original alone, which keeps you sharing it back to the network and costs you two copies of everything. Moving instead is a plain rename when both sit on the same mount, which is atomic and instant; across mounts, and separate Docker bind mounts count as separate here even on one disk, it copies, checks the arrival by size **and** SHA-256, and only then deletes the original. A failed check leaves the original exactly where it was and bins the suspect copy, so a retry still has something to retry. If the file lands but the original refuses to be deleted, on a read-only mount or awkward permissions, the download succeeds and the log grumbles, because failing a perfectly good download over housekeeping helps nobody. Folders left empty are swept up on the way out, stopping the moment anything else is in them and never touching the downloads root itself. Default stays copy on purpose: taking files out of your share directory is a decision about your standing on Soulseek, and that is yours to make.

YouTube throttling remains upstream behaviour rather than something a runtime can cure, but the bounded retry policy above now gives a transient 403 a fair second chance instead of instantly pretending the search was empty.

That was a slur on MusicBrainz, which has the record perfectly well, dated 2013-05-06 and typed EP. The typing is the whole problem: MusicGrabber asked for `type=album` and nothing else, so Knife Party's entire discography came back as one entry, *Abandon Ship*, and the album browser then politely invited you to pick the right album manually from a list of one. Electronic, hip-hop and punk acts came off worst, being the ones who release EPs for a living. The artist album list now asks for albums **and** EPs, and each entry says which it is, so six near-identical entries where there used to be one is not a mystery. Compilations, live albums, soundtracks, DJ mixes and remix records are still shown the door, and that filter now applies to EPs too rather than only to albums. Singles stay out on purpose, or a prolific artist's list becomes a hundred one-track entries standing between you and the records. Knife Party now lists *100% No Modern Talking*, *Rage Valley*, *Haunted House*, *Abandon Ship*, *Trigger Warning* and *Lost Souls*, and clicking that album link lands on the right EP with its four tracks showing, "EDM Death Machine" among them. Watched artists with "automatically add new albums" switched on inherit the wider net, which is the point; do note that the first refresh after upgrading also sees every EP the artist already had and will queue the lot, once.
- **Soulseek results stop crediting the folder somebody happens to file their music in**: fixing the peer-username attribution revealed the layer underneath. A live search for "paramore - ignorance" returned five results whose artists came out as `Paramore`, `Musique`, `FLAC Archive`, `02 - Ignorance.flac` and `P`; one in five, and the wrong four were a language, a format, a filename and an alphabetical bucket. The old rule was "the first folder that isn't on a short blocklist", which on Soulseek is a coin toss, because everyone files their music differently and quite a few file it by first letter. The path parser now knows what filing looks like, reads the artist from the folder above the album rather than the first one it trips over, and, crucially, uses the fact that the search already told us who we were looking for: given a query artist, it goes and finds them in the path instead of guessing from position. Position remains the fallback for when nobody said. The same pass pulls out the album, the release year and the track number, coping with `Artist - Album`, `[2009] Album`, `2009 - Album`, `Album (2009)`, `CD1` subfolders, underscores-as-spaces and filenames that have had the whole path stamped into them. Self-titled albums survive, and so do albums that are just a year: Taylor Swift's *1989* keeps its name. All five of those results now say Paramore. The "Related searches" chips are fixed by the same change, having previously offered to find you more music by `2jqll9htuy62asp1wu`.
- **A file that already knows its own track number is no longer talked out of it**: a Paramore download arrived correctly tagged "2 of 14", was filed as `2 - Ignorance.flac`, and ended up tagged track 15 of 16. Two faults, stacked. First, the main tagging pass has always preferred the source file's own tags over a MusicBrainz guess, and then routing the file into its album folder retagged it straight from MusicBrainz and undid that, which is a fine way to have a safeguard and no benefit from it. Both routing paths now go through the same resolver as everything else, so what the file says about itself survives the trip. Second, and the reason MusicBrainz had a wrong number to offer: the release scorer duly rated "Promo Only: Mainstream Radio, January 2010" at **-20**, then picked it anyway, because it was the only release that recording appeared on and `max()` of one dreadful option is still that dreadful option. Compilations, live albums, soundtracks, DJ mixes and Various Artists releases are now refused as album context outright rather than merely disliked; the artist and title are kept and the album, year, track position and cover art are left blank. A blank album tag is obviously missing, whereas a wrong one just gets believed.
- **“Convert to FLAC” no longer secretly means “convert to whatever the format setting says”**: Karl's Monochrome downloads were arriving as 265 kbps Opus despite starting life as genuine FLAC, which was the software doing exactly as it was told and telling nobody. The flag has never meant "make me a FLAC"; it means "convert to `AUDIO_FORMAT`", which through most of v3 quietly meant Opus. It is now called `convert_audio` everywhere: request models, browser payloads, every API response, every internal function, and the `jobs`, `bulk_imports`, `watched_playlists` and `watched_artists` columns, which are renamed in place on first boot with their values intact. The stored `default_convert_to_flac` setting becomes `default_convert_audio` in the same pass. No more reading a job row saying `convert_to_flac = 1` next to `audio_quality = "OPUS (from FLAC)"` and wondering which of the two is lying. Old spellings still work on the way in: `convert_to_flac` is accepted on every request, the old field is still emitted in responses, and `DEFAULT_CONVERT_TO_FLAC` is still honoured as an environment variable, so nobody's compose file changes behaviour on upgrade. Settings now also raises a visible warning when Opus, MP3, or lossy AAC-in-M4A is selected, since feeding those a genuine FLAC is a deliberate quality downgrade. Watched-playlist confirmations report the real selected target instead of hard-coding FLAC and Opus. Note that the column rename is one-way: rolling an upgraded database back to v3 will not end well.
- **Soulseek library roots no longer get record deals**: fixing the peer-username attribution exposed the next layer down: only one of five live results for `Paramore - Ignorance` guessed Paramore from its remote path; the others credited `Music (FLAC)`, `complete`, `Musique`, and the alphabet bucket `P`. Those segments are addresses, not artists, and passing one into MusicBrainz weakened the very lookup meant to correct it. Soulseek acquisitions now stay in per-job staging after download and integrity validation, where MusicGrabber reads the raw file's embedded `ARTIST` tag before duplicate detection, metadata lookup, tagging, naming, or library placement. A usable tag wins; blank and explicit `Unknown Artist` tags retain the old path fallback. The tag is cleaned of control characters before it reaches a query or filesystem path, and the staging directory is removed on success or failure. Untagged shares still behave as before, but a properly tagged FLAC can no longer be filed under whichever shelving convention its peer happened to favour.
- **Soulseek downloads are no longer credited to the stranger who shared them**: also reported by Syrius-consulting, and a sight to behold: a Paramore track tagged as being by `2jqll9htuy62asp1wu`, then filed in the library under that name. slskd had worked the artist out correctly from the file's own path all along (`...\Music\Paramore\Brand New Eyes\2. Ignorance.flac`), but the API threw it away, hardcoding the artist to nothing before handing results to the browser. With no artist to use, the frontend fell back to the "channel" field, which for every other source is the uploader and for Soulseek is whichever peer happens to be sharing the file. Results now carry the artist and the peer separately, so the browser shows both and tags the right one. The download side also refuses an artist that is merely the peer's username, so retrying an older job cannot resurrect the problem. Longstanding rather than new, since v3.0.3 at least; it was simply unreachable while Soulseek search itself was broken, and fixing that uncovered this. While in there, the two places that shape search results for the browser were merged into one, because they had quietly drifted apart and that is precisely how a fix gets applied to one and not the other.
- **Soulseek search results reach the screen again**: reported by Syrius-consulting, whose slskd was plainly doing its job (517 files, 250 responses, search complete) while MusicGrabber displayed absolutely nothing. The giveaway was in the log: `cannot access local variable 'adjusted_score' where it is not associated with a value`. v3.1.0 renamed the running score from `adjusted_score` to `relevance_score`, but only where it is first set and where it is read back out; the five lines that stack the source-trust, lossless, hi-res, free-slot and fast-uploader bonuses kept the old name. Python does not mind until the line actually runs, and the blanket error handler around the search then swallowed the result, so the very first file good enough to be worth having took the entire loop down with it before a single result had been collected. Anyone whose searches happened to match nothing well never reached those lines and saw an ordinary empty result, which is exactly how this hid for a whole release. The bonuses now land on the score they were always meant to, so lossless and hi-res Soulseek shares outrank a 320 of the same track again. Introduced in v3.1.0 and present in every build since; v3.0.3 and earlier were unaffected.

- **Searches now queue for a busy source instead of pretending it came back empty**: every provider has a single admission slot so that several searches cannot pile onto it at once, but that slot was grabbed non-blocking, which suited exactly one caller and nobody else. An impatient user retyping their query wants an instant refusal; a bulk import wants to wait its turn, because for it a refusal is indistinguishable from "nobody has this track" and the track is written off permanently. Callers now say how long they are prepared to queue, and the figure was measured rather than guessed: a YouTube search takes about two and a half seconds on an idle box but five to seven under any real load, so a wait has to comfortably outlast the search in front of it or it may as well not be a wait at all. Both sit inside the existing search deadline, and you only ever wait at all when something else is genuinely running. Six simultaneous searches for the same source used to leave five with nothing; they now all return results, arriving politely one after another. Busy is also reported as its own thing rather than being lumped in with errors, so an import can tell "we asked and there is nothing" from "we never got round to asking", and a track is never failed for a search that did not happen. The single-source endpoint answers a genuinely busy provider with a 503 and a `Retry-After` rather than a 500, since nothing has actually broken and an internal server error is an alarming way to say "try again in a moment". Both waits are tunable via `SEARCH_SLOT_WAIT_INTERACTIVE` and `SEARCH_SLOT_WAIT_AUTOMATED`.
- **Album downloads now ask for the album, instead of hunting each track down separately and hoping**: RAYE has released two albums four years apart, and both of them end on a track called "Fin.". Downloading the 2023 one, MusicGrabber searched for "RAYE - Fin.", got two identical-looking results with nothing to separate them, picked the wrong one, filed it neatly as track 15 of *My 21st Century Blues* and reported complete success. Album grabs now match the release as a whole against Deezer first, then take each track from that one album, so a track can only ever come from the record you actually asked for. It also swaps N chances of catching a provider mid-wobble for two, which is the other half of the problem. Anything the album match cannot place, and any album that simply is not there, falls through to the old per-track search exactly as before; a partial answer is still a useful answer. Verified on both RAYE albums: 17/17 and 15/15 tracks pinned to the correct release, every ISRC agreeing with what MusicBrainz said independently, and "Fin." finally landing on the album it was written for.
- **A source having a brief moment no longer costs you two thirds of an album**: a 17-track album came back with 4 tracks and 13 marked "No results found", which was a lie; every one of them was sitting there on Monochrome, top of the list, minutes later. The cause was close to home. Each provider gets a single admission slot so abandoned searches cannot pile up, and queueing two albums at once meant two importers racing, with the loser told "busy" by every source simultaneously. That reads as "nobody has this track", and a track marked failed is never looked at again. Searches that come back empty now get three goes with a widening pause between them, so a momentary collision costs a few seconds rather than the track. A track genuinely nobody has still fails, honestly, after all three.
- **The download card now names the source that actually delivered the file**: a track showing a YouTube badge and a YouTube link turned out to be a Monochrome FLAC on disk, correctly tagged and everything. The YouTube copy had been rejected for running 215s against MusicBrainz's 191s, retried on Monochrome and downloaded properly, but nobody told the job record, so the card kept wearing the badge of the take that went in the bin. It now updates itself when it changes horses, like its sibling fallback already did. While in there, the "Duration" line on that card was actually how long the job took, which next to "Stored: OPUS" and "Original: FLAC" read alarmingly like the track being 87 seconds long. It now says "Took".
- **Artist search stopped hiding artists who spell their name in capitals**: searching "Raye" offered a single result, and it was an anonymous feature credit on a Dead Prez record. RAYE the English singer was in MusicBrainz all along, scoring 100 to the impostors' 85, but the ordering put exact capitalisation above relevance, so three obscure acts spelled "Raye" outranked the one spelled "RAYE". The search box then compounded it: seeing an exact name match at the top, it collapsed the entire list down to that one wrong answer, and the artist you wanted was never drawn on screen at all. Name matches still come first as a group, but MusicBrainz's own relevance score now leads within that group, with capitalisation demoted to a tiebreak for when scores are level. The picker only collapses to a single candidate when exactly one artist genuinely owns the name; when several share it, as four acts do with "Raye" and three do with "Adele", you get the field and the disambiguation text that tells them apart. Unambiguous artists like Radiohead still resolve to one row and one click.
- **Lossless upgrade sources no longer masquerade as lossless final files when conversion is enabled**: Watched Upgrades now shows both halves of the operation, for example `LOSSLESS source → Opus 256 kbps output`. Lossless is still a useful clean input for a higher-bitrate lossy replacement, but the card now says plainly that the file MusicGrabber stores will be lossy. Keep-source, FLAC, ALAC, MP3 VBR, and AAC-in-M4A targets are labelled according to the same server settings the upgrade worker actually uses.
- **Watched playlist counts now describe the playlist, not its entire life story**: reported by Tristan, whose 150-track "All Out 90s" claimed 244 tracks with 158 downloaded, and whose Beatport Top 100 confidently reported 402. Every track row ever recorded was being counted, so a chart that churns weekly accumulated numbers that described its history rather than its contents, and "158 downloaded of 150" is not a sum anybody should have to defend. Worse, only mirror mode ever recorded that a track had left the upstream playlist, so for append-mode playlists the database genuinely could not tell you what was in the playlist today. Departures are now recorded whatever the sync mode, because "this track left" is a fact and not a matter of opinion; what each mode *does* about it is unchanged, with mirror dropping them from the M3U and append keeping them, and neither ever deleting a single audio file. The card now reads "50 tracks, 48 downloaded" with any leftovers shown separately as "kept from earlier" or "no longer upstream", so the archive is still visible without pretending to be the playlist. The Missing panel in mirror mode also stops listing tracks that left the playlist, since chasing those meant hunting down music the playlist had already changed its mind about, and the track list's summary and section headings now agree with each other instead of counting departed tracks twice. Verified against a real 50-track chart carrying 135 rows: 135/118 became 50 tracks, 40 downloaded, 85 kept from earlier.
- **The M3U toggle now admits what it does and does not do**: turning it off stops MusicGrabber updating the playlist file, but the `.m3u` already on disk stays exactly where it is, which understandably read as "it is still creating one". Nothing has changed about the behaviour, because a UI toggle quietly deleting a file in your library is not an improvement; the tooltip now says so plainly, and you can delete the leftover yourself if you want it gone.
- **"database is locked" no longer ambushes bulk imports, or anything else trying to write**: reported by Tristan, who found bulk imports dying on `sqlite3.OperationalError: database is locked` and, separately, could not change the preferred source on some watched playlists. Both had the same cause, and it was not contention in the way it looked. A `SELECT` whose rows are not all read leaves a read transaction, and therefore a WAL snapshot, open on that pooled connection. The moment any other connection commits, that snapshot is stale, and the next write on the connection fails **instantly** with SQLITE_BUSY_SNAPSHOT, reported to Python as "database is locked". `busy_timeout` never helped because there was nothing to queue behind: sqlite was not asking us to wait, it was refusing outright. The pool being LIFO added a lovely finishing touch by handing the freshly poisoned connection straight back out to the next caller. Pooled connections now have their cursors closed and any transaction rolled back when they go back in the pool, so no half-read query can sabotage the next borrower, and a write that still hits a lock error gets reset and retried with backoff instead of exploding. Genuine writer-versus-writer contention now also gets several goes rather than one, with the sqlite busy timeout tunable via `DB_BUSY_TIMEOUT_MS`. A mid-transaction lock error is still raised rather than retried, because quietly discarding half a transaction to "fix" an error would be a considerably worse bug than the one being fixed.
- **A bulk import no longer abandons every remaining track because one row upset it**: the handler that records a track as failed did its own database write, so when *that* write hit the locked database above, the exception escaped the loop and took the rest of the import with it. This is exactly what Tristan's traceback showed: one error during handling of another, and a worker walking off the job. Recording a failure can no longer become the failure; it is logged and the import carries on with the next track.

## v3.1.0 (2026-08-04)

### Added
- **ReplayGain tags on new downloads, opt-in and completely non-destructive**: MusicGrabber measures each finished download and writes ReplayGain 2.0 track gain and peak tags against the standard -18 LUFS reference, then lets your player do the actual turning-down. Unlike loudness normalisation it never re-encodes a single sample, so it is safe on lossless files and entirely reversible. Album gain and peak are added once every track on a record has landed, calculated across the album so quiet interludes stay quiet instead of being bullied up to match the singles. Existing ReplayGain tags are left alone unless you explicitly ask for them to be replaced, because whoever wrote them probably meant it. FLAC, MP3, M4A, Ogg and Opus supported; WebM continues to have nowhere to put them.
- **MusicBrainz release URLs now download as proper albums**: paste a `musicbrainz.org/release/…` or `/release-group/…` link into Bulk Import and it goes straight down the album pipeline, landing in `Albums/Artist/Album/` with cover art, an `.albuminfo` sidecar and reliable track numbers, rather than being flattened into a list of "Artist - Title" lines bound for Singles. The MBID is already in the URL, so there is no scraping and no guessing which "Greatest Hits" you meant. Release-group links resolve to the earliest official pressing.
- **A minimum-quality filter on search results**: the Tracks tab can now hide anything below 192, 256, 320 kbps or lossless. It is honest about its limits, mind you: only Soulseek, Monochrome and FreeMp3Cloud declare a quality before you download. YouTube and SoundCloud say nothing at all, so they count as "undeclared" and are hidden the moment you set a minimum, because asking for lossless and being handed a YouTube rip is nobody's idea of a filter. Tick "Keep undeclared" if you want them back. Do bear in mind that results are still ordered by how well they match your search rather than by audio quality, which is why an undeclared result could otherwise sit cheerfully above three real FLACs. Your choice is remembered between searches.
- **A full-library Audio Provenance Audit has arrived under Watched**: the manual, read-only scan covers supported files throughout the configured music directory, including Albums and historical files, while excluding symlinks and known staging/quarantine paths. It separates stored codec from recorded acquisition history, recognises known lossy transcodes, native lossy acquisitions, lossy derivatives, recorded lossless acquisitions, unknown history, and unreadable files, and shows the evidence and caveats behind every row. Container, codec, source, effective-quality, and two honestly different lossless filters are included, as are authenticated CSV/JSON dry-run exports. Completed reports publish atomically, interrupted runs recover honestly, and the scanner deliberately yields to ordinary library traffic rather than turning a large NAS into treacle. Nothing is renamed, retagged, moved, deleted, replaced, spectrally blessed, or sent into Watched Upgrades yet.

### Changed
- **The "Results" tab is now called "Tracks"**: same tab, same single job of searching for and downloading one track at a time, a name that finally says so. Requested on reddit, and it turns out "Results" was only ever a description of what happened rather than what the tab was for.
- **Low NAS service IDs are documented without the false alarm**: TrueNAS commonly runs applications as `568:568`. Debian's account tool warns that UID 568 sits below its normal interactive-user range, but MusicGrabber still starts, runs and writes as 568 correctly. The permissions guide now identifies that message as cosmetic and points at the host dataset ACL, which is the bit that can actually stop a download landing.
- **Search ranking now calls itself relevance, because that is what it is**: the combined artist/title match, views, duration and source bonus is now `relevance_score` throughout all six search adapters, aggregation, automated selection, the browser and API responses. The old `quality_score` name made it sound like a YouTube title match could somehow measure a codec. Actual audio quality remains the separate `quality_tier` used by the minimum-quality filter; Soulseek's internal codec/bitrate quality component remains exactly that. API clients reading search results should switch to `relevance_score`.
- **The README's "Why?" has caught up with the last two years**: it still described a tool that grabs one song off the radio, which remains perfectly true and remains the point, but rather undersold the watched playlists, watched artists, lossless sources, album mode, provenance auditing and multi-user support that have arrived since. It now says what MusicGrabber started as and what it has become, while leaving "What this project is not" to keep the ambitions honest.

### Fixed
- **SMTP setup now tells you what went wrong**: Email settings have a Send Test Email button which exercises the same connection, STARTTLS, login and delivery path used by real notifications, including unsaved form values while retaining an already-saved masked password. Failures now distinguish bad DNS, timeout/refusal, STARTTLS, authentication, sender and recipient errors instead of disappearing into a bare `except`. The old “Use TLS” label now says what it actually does: STARTTLS (normally port 587; implicit TLS on 465 is not supported).
- **Two downloads of the same track no longer sabotage each other**: this was logged as a flaky thumbnail CDN, and it was nothing of the sort. Every download wrote its working files straight into the destination folder, all named after the track, so two jobs for the same song running at once would cheerfully delete each other's `.part`, `.webp` and final files mid-flight. Whichever one reached for a file the other had just tidied away died with a baffling "No such file or directory", and since yt-dlp converts cover art *before* it fetches any audio, the thumbnail was usually first to go and therefore got the blame. Reproduced live: three jobs for the same track failing within seconds of each other, one on a missing `.webp`, one on a `.part` rename, one on a vanished `.webm`. Each download now works in its own staging directory under the music root and only the finished audio is moved into the library, so the collision is structurally impossible rather than merely unlikely. Anything abandoned by a hard restart is swept at startup. This was reachable in normal use whenever the same track sat in two watched playlists refreshing together, or twice in one bulk import.
- **A fumbled piece of cover art can no longer take the whole download with it**: found while chasing the above, and worth fixing in its own right. yt-dlp runs `--convert-thumbnails` as a `before_dl` postprocessor, so if the thumbnail file is missing it raises a bare `FileNotFoundError`, and yt-dlp's own handler only catches `PostProcessingError`. The job is abandoned on the spot with no audio file at all, and the existing salvage path could not help for the very good reason that there was nothing to salvage. A download that fails on cover art now gets one more go with thumbnail embedding switched off, which costs essentially nothing: MusicGrabber replaces the video thumbnail with proper album art from Cover Art Archive, iTunes or Deezer moments later anyway. Losing a track because a CDN dropped a JPEG we were about to throw away was never a good trade.
- **MusicGrabber now answers in about a second instead of making you wait half a minute**: starting the container used to leave the web page unreachable for 30 seconds or more, and the culprit was a magnificently self-inflicted one. The database connection pool only ever fills up as connections are handed back, so in a freshly started process it is empty; the checkout code treated "empty" as "everyone is busy" and dutifully waited out its full 15-second timeout before opening the connection it could have opened immediately. That happened on the very first query of every boot, before uvicorn had so much as opened the port. The pool now grows on demand up to its ceiling and only blocks once every connection is genuinely on loan, which is the case it was written for. The startup housekeeping pass has also moved into the background thread that already runs it on a schedule, so reconciling deleted files against a sleepy NAS no longer stands between you and a web page. Measured on a local container: 15.9 seconds down to 0.8, and under a second on restart.
- **A first-load panel, so an empty page stops looking like a broken one**: even once the server is up, there is a moment while 400KB of application JavaScript arrives during which the app shell sits there unpopulated, looking convincingly like something has gone wrong. A small pure-HTML panel now paints immediately and steps aside the instant the app is ready, whether that lands you on the app, the login screen, or a config request that fell over. It also picks up your saved theme before the first paint, so light-theme users are no longer greeted by a brief flash of the void.
- **A manual choice no longer gives CDN previews diplomatic immunity**: selecting a result by hand deliberately bypasses MusicBrainz's canonical duration check, because sometimes you really do want the live version, radio edit or twelve-minute remix. That exemption also let a valid-looking 30-second CDN sample pass as a finished four-minute song. The Tracks UI now sends the duration advertised by the exact result clicked, and the job retains it only with a valid server-issued search token. If the downloaded audio is substantially shorter than that result, it is rejected and recorded as preview audio; matching live/remix/edit durations still pass, even when MusicBrainz disagrees. An incomplete manual pick fails honestly instead of silently replacing your deliberate version with somebody else's idea of the right one.
- **Bootleg-heavy MusicBrainz catalogues no longer hide the studio take**: recording search could return the same confidently wrong answer every time when live bootlegs filled its shortlist. At the production limit, “Karma Police” repeatedly landed on a one-release live recording attached to *Hail to the Thief*. A weak result now gets a targeted release-group fallback: MusicGrabber finds the exact-title single or EP, follows the recording reused across its official editions, then browses that recording's albums for stable release context. Live checks now put “Karma Police” on *OK Computer*, “Around the World” on *Homework*, and “Teardrop” on *Mezzanine*, complete with track numbers. The extra requests are reserved for weak results; repeated searches showed no material run-to-run variance, so ordinary MusicBrainz lookups have not acquired a permanent third wheel.
- **Watched-playlist source exclusions now survive the entire download journey**: a playlist's selected sources were correctly saved and used for the first search, then quietly abandoned if the chosen download failed; the cross-source fallback and Queue retry searched every enabled provider and could land a track from one the playlist had explicitly deselected. An unavailable or globally disabled selection could also make the initial search expand back to all sources. Source selections are now strict allow-lists through initial import, scheduled refresh, automatic fallback, candidate download and manual retry. If the allowed providers cannot deliver, the track fails honestly instead of coming home through the tradesman's entrance. SoundCloud's first import now also uses the same implicit SoundCloud-only selection stored on its watched-playlist row.
- **Thirty-minute watched checks now happen every thirty minutes, not whenever tomorrow happens**: per-playlist and per-artist intervals were used only to decide whether something was due after the background scheduler woke, while the scheduler itself slept for the global `WATCHED_PLAYLIST_CHECK_HOURS` default of 24 hours. A half-hour watch was therefore checked roughly daily, and restarting looked like a cure because startup performs an overdue pass. Both schedulers now sleep until the earliest enabled item is due, capped by the global interval, and additions or schedule changes wake them immediately to recalculate. The initial playlist fetch is stamped as its first check so adding a watch does not immediately fetch it twice. “Last checked” now shows a useful relative age with the exact local timestamp on hover instead of displaying only the date, which had been hiding every same-day refresh for good measure.
- **Monochrome downloads went from half a minute to a fifth of a second**: measured end to end, a Monochrome track took 37 seconds to resolve; it now takes 0.2 seconds once the first one has landed. Two things were to blame, and neither was Monochrome's fault. First, the shared qbdlx token pool holds 28 tokens of which precisely 3 still work, and they sit at the very bottom of the list, so every single download re-walked the same 25 duds from the top before finding one that could deliver. We now remember whichever token actually worked and try it first, falling back to the full walk when it inevitably rots. Second, two of the three default Qobuz proxies were beyond help: `qobuz.kennyy.com.br` answered with a Cloudflare 522 only after burning a 20-second read timeout, and `qdl-api.monochrome.tf` has no DNS record left at all. A v9 database migration retires both, keeping any self-hosted URLs you have configured. `mono.scavengerfurs.net` survives on the grounds that it fails in half a second and might yet be resurrected.
- **Monochrome downloads landing as 30-second previews**: the qbdlx direct-Qobuz fallback (the leg that carries every Monochrome download whenever the third-party proxies are having a bad day, which lately is most days) picked the first token in its shared pool that returned any URL at all. It never checked whether Qobuz had quietly downgraded that token to sample-only. Several tokens in the pool now hand back a 30-second, ~1.2MB MP3 flagged `"sample": true` no matter which FLAC format was actually requested, and the code was cheerfully treating that as a finished lossless download. It now skips sample-only tokens and keeps walking the pool until one hands back the genuine article, matching the same "reject a preview, don't save it" principle from the old hifi-api days. Reported by Piranhaz on [GitLab #71](https://gitlab.com/g33kphr33k/musicgrabber/-/work_items/71).
- **One missing Qobuz track could blind the whole of Monochrome for ten minutes**: a download failing because the entire leg is down, and a download failing because one obscure b-side genuinely isn't on Qobuz or Tidal, raised the exact same exception. The code took either as proof the whole source was broken and parked Monochrome out of every search for a full cooldown over a single unlucky track. A failed download now re-probes the leg itself, the same live check the scheduled health probe already uses, before deciding whether to park anything; a missing b-side no longer costs everyone else their lossless results. The qbdlx shared token pool got some housekeeping to go with it: a token proven dead or downgraded to a sample is now remembered and skipped for the rest of that pool's ten-minute cache cycle instead of being re-tried on every subsequent track in a playlist, the last known-good token now survives a container restart via the settings table instead of forgetting everything on every redeploy, and health-check reasons now report a live "N/M shared tokens usable" count instead of a bare pass or fail, so a rotting pool shows up before it goes fully dead rather than only after.
- **Singles finally get their track number**: downloaded tracks have been arriving with no track-number tag even when MusicBrainz knew full well which track it was. Two separate causes, both now sorted. The MusicBrainz *search* API nests the matched track under `track` while the *lookup* API uses `tracks`, and we were only ever reading the plural, so the text-search path came back empty-handed every time. Meanwhile the fingerprint path was asking for releases without asking for their media, so the track listing it then searched simply was not there. Vinyl pressings that print "A1" instead of "3" now fall back to the position within the disc. Reported by RxBrad.
- **Library scans no longer count everything you have ever deleted**: Synology, QNAP and Windows SMB shares keep deleted files in a hidden bin *inside* the share, so the upgrades scanner, the provenance audit and the Stats storage figure were all cheerfully walking into `@Recycle`, `#recycle`, `.Trash-1000` and friends. Track upgrades were being offered for records binned weeks ago. All three scans now share one walker that skips those folders (plus `@eaDir`, `System Volume Information`, `lost+found` and the macOS metadata caches) and refuses to follow symlinks out of the library. Albums genuinely called *Trash* are quite safe; only the bins with a leading dot, hash, at-sign or dollar are excluded.
- **Downloads now land on the album they actually came from**: MusicBrainz scores text matches on string similarity and nothing else, so all 25 recordings of "Praise You" tie on 100 and the order between them is arbitrary. Asking for a single result was therefore not asking for the most likely album, it was drawing a raffle ticket, and the raffle was not even repeatable: three identical searches for "Radiohead - Karma Police" returned 50 different recordings with none common to all three. Measured against a new 31-track corpus covering bootleg-heavy, compilation-heavy, mainstream and non-English tracks, the old behaviour scored 3.7 out of 31. MusicGrabber now asks for a proper shortlist, asks a second time with a studio-album filter, merges the two, and works out which recording is the canonical take before choosing a release from it. That scores 26 out of 31 against the live API and improves every category tested. "Around the World" now arrives on *Homework* instead of the live album *Alive 2006*, and "Smells Like Teen Spirit" on *Nevermind* rather than a Bristol bootleg. Compilations, DJ mixes and "(Boombox Rehearsals)" takes now lose on purpose.
- **Romanised non-English titles find their metadata at last**: searching for `Yoru ni Kakeru` matched no recording title and quietly returned nothing at all, because MusicBrainz files that track under 夜に駆ける. Same for `Gruppa krovi` against Группа крови. When both searches come back empty we now try once more against aliases, which is where transliterations live, and the track comes back correctly tagged in its native script. Tracks whose title is a different rendering rather than a variant are no longer treated as suspicious, so this does not fight the album picking above.
- **Featured-artist credits no longer leave owned tracks stuck in Watched → Missing**: playlist services may call a track `The Chemical Brothers, Q-Tip - Go` while the file, Navidrome, and Lidarr file it under `The Chemical Brothers - Go`. Local, Navidrome, and Lidarr duplicate checks now try the complete credit first and the primary artist as a fallback. When an ordinary Search download then succeeds, or politely reports that you already own it, equivalent unresolved watched rows are reconciled for that user, their real path is retained when available, and affected M3Us are rebuilt. Four databases may still disagree about the guest list, but they no longer get four votes on whether the song exists.
- **Collaborations no longer get a stray double space in the artist tag**: MusicBrainz hands back each credited artist with its own separator attached (" & ", " feat. "), and we were helpfully adding a space on top, so "Underworld & Iggy Pop" was tagged as "Underworld &  Iggy Pop". Five places in the metadata code were doing it. Single-artist tracks were never affected, which is precisely why it survived this long.

### Added
- **The Queue now says what it is actually doing**: a live workbench summary shows how many tracks are downloading and how many are waiting, each active job shows its current stage and a second-by-second elapsed time, and the last-refresh indicator makes it obvious the page is still listening. When everything is finished, the queue puts its feet up; while it is busy, tiny hammers are apparently involved.

### Changed
- **Audio conversion now says exactly what it will do**: the header and watched controls show either `Keep source` or `Convert to [format]`, and Settings presents those as the two explicit choices instead of showing a row of formats without the on/off decision. The expanded explanation makes clear that FLAC/ALAC preserve lossless input but cannot restore quality already lost by MP3, AAC, Opus, YouTube, or SoundCloud sources. Fresh installations keep source formats by default; existing saved choices are left alone.
- **Queue polling now matches the amount of work happening**: active downloads refresh every 1.5 seconds so stage changes and completed tracks appear promptly, then the page backs off to every five seconds once the queue is idle. A separate local timer keeps elapsed times moving smoothly without hammering the API once a second.
- **Loading and empty states have been given words as well as wheels**: Search changes its button to “Searching…” and explains that it is warming up the search party, the Queue says it is taking attendance while loading, and a virgin queue is now suspiciously quiet rather than merely blank.

Refresh now revisits unresolved historical rows against MusicGrabber's library, Navidrome, and Lidarr; heals `downloaded_at` and the real media path when a match appears; stamps the playlist Comment tag when enabled; and makes the recovered file eligible for the next M3U rebuild. Historical tracks that have left the source are deliberately never re-queued, so reconciliation repairs playlist state without turning an old chart into a surprise bulk download.
- **Historical library checks are persistent and bounded**: the database now records `library_checked_at` for each retained playlist track. A first refresh after upgrade performs the repair pass automatically, genuine misses are retried periodically instead of on every button press, and independent external lookups use a small worker pool plus a refresh-scoped Lidarr catalogue cache. The retry interval defaults to 24 hours and can be adjusted with `WATCHED_HISTORY_RECHECK_HOURS`.
- **Watched Upgrades now explains the quality comparison it is actually making**: each current track distinguishes the stored codec/bitrate from the known original codec/bitrate and its effective tier. A 622 kbps FLAC made from a 128 kbps MP3 therefore says exactly that instead of looking as though its FLAC container bitrate is being compared with Monochrome's `LOSSLESS` badge.

### Fixed
- **Search and watched playlists now agree about tracks already managed by Lidarr**: the interactive duplicate check consulted Lidarr, but watched refresh only consulted local files and Navidrome. A track could therefore be reported as “already in your library” in Search while the playlist continued to call it missing. Watched refresh now uses the same local → Navidrome → Lidarr resolution chain, retains absolute Lidarr paths for M3U entries, and honours existence-only sentinels without writing unusable paths.
- **Append-mode chart history no longer stays falsely “missing” after a song leaves the chart**: refresh previously iterated only the tracks returned by the latest upstream fetch. Historical rows were kept, as append mode promises, but were never visited again, so no later library acquisition could heal them. They now participate in the reconciliation pass described above and immediately disappear from Missing once a real match is found.
- **Genuine lossless files are no longer demoted by an ambiguous legacy quality label**: upgrade classification now prefers the structured `SOURCE_CODEC` and `SOURCE_BITRATE` provenance tags, using the older display string only as a compatibility fallback. Lossy transcodes remain correctly eligible, and lossy-to-lossy conversions are capped by both the input and output quality rather than inheriting whichever bitrate happens to be larger.
- **A newer toast can no longer be hidden by an older toast's timer**: showing another notification now cancels the previous dismissal timer, and its display time scales with the amount of text instead of every message vanishing after the same hurried 2.5 seconds.
- **Queue progress timestamps are now unambiguously UTC**: `progress_at` receives the same timezone suffix as job creation and completion timestamps in both job APIs, so browsers outside UTC do not quietly interpret a fresh heartbeat as local server time.
- **The source-health strip no longer sits on the search box**: its negative top margin cancelled the search field's intended breathing room, leaving the source chips clinging to the lower border. The strip now keeps a proper gap before the tabs on desktop and mobile.
- **The Albums tab once again picks up where a singles search left off**: after a successful track search, opening Albums carries the artist across and immediately looks up the MusicBrainz artist choices. Existing album work is left untouched, direct album links keep their faster exact-match route, and Results-only furniture (related searches, explore controls, search progress and destination picker) no longer follows you into every other tab looking lost.

## v3.0.1 (2026-07-18)

Development cycle opened after v3.0.0. The kettle boiled, then promptly needed refilling: two of the cheap MP3 sources had quietly changed addresses without leaving a forwarding note.

### Fixed
- **Searches no longer open with up to half a minute of dead air when a health check goes stale**: the multi-source search ran source health probes synchronously before emitting a single event, and Monochrome's probe sweeps every Qobuz proxy at 8 seconds apiece, serially, for maximum suffering. Probes now run in a background thread while the search serves the last-known verdicts instantly, the proxy sweep runs in parallel, and concurrent searches share one probe instead of forming an orderly queue behind a corpse. Bonus fix: the probe pool's timeout was decorative (a `with` block waited for the slowest probe anyway); it now actually walks away.
- **Monochrome downloads with dead proxies no longer grind for up to 15 minutes before another source gets a go**: the retry ladder multiplied quality tiers by proxies by retry rounds (3 x 3 x 5, at 15 seconds a call) before the cross-source fallback was allowed anywhere near the job. The download leg now skips proxies already known to be down (the search leg has done this for ages; the memo finally arrived), a proxy that times out is parked on first offence, and when every proxy is transport-dead we stop stepping down quality tiers (dead for HI_RES is dead for LOSSLESS, funnily enough) and head straight for the qbdlx fallback. Worst case is now around a minute.
- **The stale-job reaper no longer shoots slow-but-alive downloads**: it judged jobs purely on age since creation, so anything legitimately busy past 15 minutes was marked "Timed out (no progress)" while its worker was still beavering away. Jobs now carry a proper progress heartbeat (bumped on every job update, reset on retry) and only get reaped when that actually goes quiet.
- **Soulseek results finally have stable identities**: result ids were minted randomly per search, so blacklisting a bad file or excluding an already-tried one never stuck; every retry was a fresh case of amnesia. Ids are now derived from who's sharing which file, so the same file gets the same id every time.
- **zvu4no search stopped returning anything**: the site rebranded from zvu4no.org to zvu4it.org (the old domain still redirects, bless it), but our download-link and thumbnail regexes were hardcoded to the old CDN hostnames, so every result got silently filtered out. Regexes are now domain-agnostic so the next rebrand doesn't do this again.
- **FreeMp3Cloud search stopped returning anything**: `g2.freemp3cloud.com` now 301s to `a2.freemp3cloud.com`, and posting the search to the pre-redirect URL was getting quietly downgraded to a GET by the redirect follow (standard HTTP behaviour, unhelpful here), so we always got the plain landing page back instead of results. Now posts to wherever the landing-page fetch actually landed.

### Changed
- **Sources that keep timing out now get parked without waiting for the next probe**: three consecutive multi-source search timeouts and servicecheck benches the source for the usual cooldown (one on-time answer wipes the slate). Stops a limping source bleeding a 500-track bulk import dry at 30 seconds per track while its scheduled health check insists everything is fine.
- **A parked source now stays hidden until a probe actually clears it**: cooldown expiry schedules the re-check rather than pardoning the source on the spot, so results that would only fall over at download time don't flicker back early. Relatedly, the Qobuz proxy failure cooldown dropped from 30 to 10 minutes; now that downloads honour the marks too, half an hour on the naughty step was a bit much for one hiccup.

### Removed
- **MP3Phoenix as a search source**: the site went from a plain 403 to a proper Cloudflare "Just a moment..." challenge, and it turns out that's not a Tuesday-afternoon fix. We tried a stealth-patched Playwright, then Patchright (an "undetected" Playwright fork that claims to beat Cloudflare outright), then FlareSolverr, running on Karl's own residential IP throughout so it was never an IP-reputation problem. FlareSolverr got furthest: it genuinely solved the challenge and fetched real search results, but its API only speaks HTML pages, not files, and it just times out against the actual MP3 download link. We also tried replaying a real cf_clearance cookie (both hand-exported from a browser and freshly minted by FlareSolverr itself, matched UA and all) through our own HTTP client, and Cloudflare still said no, so something beyond cookie and User-Agent is being checked. Rather than build our own browser automation from scratch to chase a lossy 320kbps source, MP3Phoenix has been retired. It had a good run setting the fire alarm off regularly.

## v3.0.0 (2026-07-09)

The big three-oh. What was brewing as v2.9.6 grew into a proper milestone: live search progress, a volume normaliser, self-importing downloads for macOS Music, and a tidy-up crew for playlist folders. Version number promoted to match.

### Added
- **Loudness normalisation for lossy sources** (Settings, off by default; thanks to Upstairs-Brush for the nudge): YouTube uploads range from whisper to jet engine, so there's now a toggle that levels every download from a lossy web source (YouTube, SoundCloud and the MP3 sites) to a streaming-standard -14 LUFS as it arrives. It's ffmpeg's proper two-pass EBU R128 loudnorm in linear mode, so it's a pure gain ride, no compression, no pumping, and the file keeps its sample rate (no sneaky 192 kHz "remasters" of a YouTube rip). Cover art survives the trip, tracks already at the target are left alone rather than pointlessly re-encoded, and lossless sources (Monochrome, Soulseek) are never touched; their masters stay exactly as mastered. Targets are tuneable via `LOUDNORM_*` constants for anyone who thinks -14 is for cowards.
- **Auto-import copy folder** (Settings, File Organisation; smailpouri's follow-up to the COMMENT tagging): point it at a mounted macOS Music "Automatically Add to Music" folder and every finished download quietly drops a copy in there, so tracks appear in Music without a single click. It's a copy, not a move; your library keeps its file, Music consumes the duplicate. Files land under a hidden name and only get renamed into view once fully written, so Music never inhales half a track. Per-user, and empty means off.
- **Playlist folder orphan round-up** (Watched tab, under Watched Playlists): mirror-mode removals drop tracks from the playlist and its M3U but deliberately leave the audio files on disk (deleting music is not our department). The new "Find Orphans" button sniffs out files in playlist folders that no watched playlist claims any more, lists them with their playlist and size, and offers per-track or move-all rehoming into the normal Singles layout, lyrics files riding along. Nothing moves without you clicking, nothing is ever overwritten, and shared custom folders are handled properly (a file claimed by any playlist sharing the folder is safe).
- **Live search progress**: a multi-source search no longer hides behind a single spinner wondering if it's died. Results now stream in as each source answers (best floated to the top as scores settle), with a wee status panel ticking sources off live: a spinner while it's looking, a green tick with the result count when it lands, and an honest note when one is offline ("skipped"), slow ("took too long, moved on") or having a wobble. Each row gently fades away on its own once its source has reported in, so the panel empties itself as results land rather than lingering. The status lines lean cheeky-but-factual and live in their own file (`static/quips.js`), sectioned per service with a dedicated funny-failures section for timeouts, offline sources and wobbles, so there's a big rotating pool and it's trivial to add more. Under the bonnet it's an NDJSON stream off a new `/api/search/stream` endpoint; if the stream ever hiccups it falls straight back to the old blocking search, so you're never worse off. Soulseek now rides along in the same stream as a normal source (gated on its Search Sources toggle, exactly as the Settings help has always advised), retiring the old bespoke "search Soulseek separately and interleave" dance, results are simply ranked best-first across every source now.
- **Singles search duplicate heads-up**: when a search is typed as `Artist - Title`, MusicGrabber now asks any enabled Navidrome and Lidarr integrations whether the track is already in the library, then floats a polite note above the results if it is. It is only a nudge, not a bouncer; you can still download another copy if the heart wants what the heart wants.

### Fixed
- **Monochrome can now actually find tracks Deezer's search likes to hide**: the Deezer leg searched by free text only, and Deezer's relevance ranking will cheerfully bury an exact match under a pile of fuzzy near-misses (the track that started all this, BUNT.'s "LIEBE", vanished beneath a heap of "Immer Liebe" and a German audiobook). When the query splits cleanly into "Artist - Title" we now also fire a structured `artist:"x" track:"y"` query straight at Deezer; and if that proper order draws a blank, we try the fields the other way round to rescue a query typed back-to-front (because everyone occasionally does). The reverse only kicks in when the forward order found nothing, so it rescues transposed searches without dragging funny matches into ones that were already fine. The buried track now turns up at the top instead of nowhere at all.
- **A full page of weak Deezer guesses no longer blocks the Tidal leg**: Monochrome used to stop the moment Deezer returned a full page, even when every result was a fuzzy miss, which meant the Tidal hifi-api leg (often the one actually holding the track) never got a look-in. It now only trusts a full Deezer page if one of the results is a confident match for what you asked for; otherwise it carries on and merges in Tidal's results too.
- **Monochrome no longer crawls when its Qobuz proxies are down**: each ISRC verification was trying every proxy in turn at a 15-second timeout apiece, so with the proxies offline a single search could sit there for the best part of a minute, long enough that the new search deadline gave up and dropped Monochrome (and your lossless results) entirely. Known-dead proxies are now skipped on sight (the background health probe still re-checks and clears them when they recover), so a Monochrome search that used to take ~47 seconds now comes back in well under one, and its results make it into the merged list rather than the bin.
- **Search deadline raised to 30s** (configurable via `SEARCH_ALL_DEADLINE`), so a momentarily slow lossless source has room to answer rather than being dropped. The proper long-term answer is showing search progress in the UI so a longer wait is visible and bearable rather than looking like a hang; that's on the list.

Each source is now capped at 4 results in the merged pool; scoring determines the final order
- **Disabled sources still appearing in search results**: The per-source enable/disable setting was being read with `get_setting()`, which returns a string. Checking `bool("false")` is `True`, so toggling a source off in Settings had no effect. Both the `search_all` and `search_source` paths now use `get_setting_bool()`
- **MusicBrainz duration scoring bands tightened**: The tolerance windows were calibrated for longer tracks but most songs are ~3 minutes, where 25% is 45 seconds of slop. Bands are now ≤2% (+40), ≤5% (+20), ≤10% (neutral), ≤25% (-30), >25% (-60)
- **Monochrome quality bonuses and MP3Phoenix bonus rebalanced**: The gap between lossless (Monochrome) and 320 kbps lossy (MP3Phoenix) was only 20 points after the previous round of tuning, narrow enough for a duration scoring nudge to flip the result. MP3Phoenix bonus reduced from +50 to +30; LOSSLESS raised from +70 to +80; HI_RES_LOSSLESS from +90 to +100. Clean 50-point gap: lossless always wins on equal relevance
- **Monochrome variant tracks unfairly promoted by quality bonus**: Tidal's catalogue occasionally surfaces alternate-mix variants with opaque parenthetical suffixes (e.g. "Hey Man Nice Shot (½ oz)") that score the same as the clean studio title after normalisation strips the brackets. Combined with the LOSSLESS quality bonus, these variants were ranking above the plain track from every other source. Two fixes: title variants with unrecognised parenthetical content now take a -110 penalty in the Monochrome scorer (enough to neutralise even HI_RES_LOSSLESS), and the LOSSLESS/HI_RES_LOSSLESS bonuses have been trimmed from 100/120 to 80/100 so that a stack of official signals on a YouTube result can still win. Known-benign suffixes (Remastered, Deluxe Edition, feat., etc.) are unaffected
- **Monochrome tracks ignored the audio format setting**: The Monochrome download path always wrote `.flac` and never consulted `audio_format`. If you'd set MP3 or Opus as your preferred format, YouTube downloads would convert correctly and Monochrome downloads would quietly stay FLAC. The lossless file is now transcoded to MP3 (VBR ~192k) or Opus (320k) after integrity checks and metadata embedding, same as every other source
- **Docker healthcheck ignored `LISTEN_PORT`**: The `HEALTHCHECK` instruction was hardcoded to `localhost:8080`, so any container using a non-default `LISTEN_PORT` would show as unhealthy. The healthcheck now uses `${LISTEN_PORT:-8080}`, falling back to 8080 when the variable isn't set
